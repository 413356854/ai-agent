## 一、这条路是干什么的

阶段二那条 RAG 是**离线评测链路**：语料固定在类路径、向量是本地哈希近似、检索在进程内做。
知识库是另一条链路：**文档从 HTTP 传进来 → 解析 → 切分 → 真 embedding → 落 Milvus → 检索 → 注入对话**。

两条链路**不共用索引**，互不影响。评测仍在用 `VectorIndex`（本地暴力 KNN），
知识库用 Milvus（一个知识库一个集合）。

## 二、跑起来

```powershell
pwsh scripts/milvus-start.ps1          # Milvus 必须先起：它的客户端 Bean 在启动时就连
$env:DASHSCOPE_API_KEY="sk-..."        # embedding 与重排都用这一把
cd ai-agent; .\run.cmd                 # 应用（MySQL 也要在跑）
```

不配 `DASHSCOPE_API_KEY` 时**应用照常启动**，但知识库那一族接口会明确报
`embeddingAvailable=false` + 原因，上传的文档以失败收场并写明缺哪把 key ——
不用假向量冒充真向量。

界面：`web/` 的「知识库」一区（存知识库 / 传文档 / 编译切片 / 切分预览 / 命中测试）。

## 三、接口一览

| 用途 | 请求 |
|---|---|
| 列表 + 当前能力 | `GET /api/knowledge-bases` |
| 建库 | `POST /api/knowledge-bases`（`{"name","description","chunkStrategy":"length|structural"}`） |
| 改配置 / 启停 / 删库 | `PUT /{id}`、`POST /{id}/enabled`、`DELETE /{id}` |
| 传文档（一次一个） | `POST /api/knowledge-bases/{kbId}/documents`，multipart 字段名 `file` |
| 文档列表 / 详情 / 重新索引 / 启停 / 删除 | `GET (POST) .../documents[/{docId}][/re-index][/enabled]`、`DELETE .../{docId}` |
| 切分预览（不写库、不算向量） | `POST .../{docId}/chunks/preview` |
| 切片列表（分页）/ 改正文 / 启停 / 删除 | `GET .../{docId}/chunks?offset=&limit=`、`PUT/POST/DELETE .../chunks/{uid}` |
| 命中测试（只读） | `POST /api/knowledge-bases/retrieve`（`{"kbIds":[1],"query":"…","rerank":true}`） |
| 一致性核对 | `GET /api/knowledge-bases/{id}/consistency` |
| 对话侧注入 | `/api/agent/ask` 与 `/api/chat/stream` 的请求体带 `knowledgeBaseIds: [1]` |

## 四、数字怎么读

- **`indexSize`**：这个库里**参与检索的切片数**。它是分母 —— 没有它，
  "0 条命中"与"库里就是空的"分不开。
- **`candidateCount`**：这次粗召回了多少条（进重排之前的数）。
- **`vectorScore`**：余弦相似度，越大越像。**只在同一次检索里可比**，跨查询没有意义。
- **`rerankScore`**：重排分，与向量分**不同量纲**，所以两个都显示。为 `null` = 这次没重排，
  此时一定同时给出 `rerankSkipReason`（"没开"与"开了但失败了"分得开）。
- **`chunkCount` / `indexedAt`**：文档索引的**三态**判据在界面上分三种说法 ——
  没索引过（`indexedAt` 为空）／索引成功但一块都没切出来（`chunkCount=0` 且 `indexedAt` 有值）／失败（`status=FAILED`）。
  前两种在只看 `chunkCount` 时长得一样，而处置方式相反（换文档 vs 点重新索引）。

## 五、实测数字（2026-10-17，本机）

| 项 | 数 |
|---|---|
| 索引一份 24KB 的 markdown（30 块 / 5225 token） | **3.5 秒**（2 线程池，DashScope 每批 10 条） |
| 检索一次（20 条粗召回 + gte-rerank-v2 重排 + 返回 3 条） | **377–517 ms** |
| 一份文档写完后清单与向量的条数 | 都是 30（`/consistency` 逐文档比对通过） |
| 同一句提问的向量分 / 重排分 | 0.7634 / 0.8576（重排**改变了名次**：向量分第二高的那条被挤到第三） |

## 六、已知局限（不粉饰）

1. **没跑过规模**。最大的一份文档 24KB / 30 块。索引类型目前是 `AUTOINDEX`（没调过参），
   集合大了之后召回率与耗时的表现没有被验证过。
2. **单机单进程**。索引队列与状态机都是进程内的：两个实例同时跑同一份文档不会被
   "谁抢到锁"拦住（靠的是"先删后插"+状态守卫，两者都不是跨进程的）。
3. **切片只在两处**：清单在 MySQL、向量在 Milvus。两者可能不一致（删到一半退出、手工动过库），
   所以有 `/consistency` 端点 —— 但它**只是把数字摆出来**，不会自动修复；
   修复动作是"对相关文档点重新索引"。
4. **重新索引会换一批切片 uid**：任何缓存的 uid（比如 trace 里历史命中的 uid）在重新索引后指向不存在的行。
5. **删除知识库不删原件**：`data/kb/{kbId}/` 下的文件留着，要清理得手工删目录。
6. **切片分页是 `LIMIT/OFFSET`**：一份文档切出上万块时越翻越慢（本项目没有别的分页范式，先这样）。

## 七、踩过的坑（都写进了代码注释，这里只列位置）

| 现象 | 原因 | 在哪 |
|---|---|---|
| 文档永远停在「已上传」 | 上传事务还没提交，索引线程在另一条连接上读不到那一行，**静默跳过** | `KbIndexingService#submitAfterCommit` |
| 重新索引后召回里出现重复内容 | `MilvusVectorStore` 写的是 `insert` 不是 `upsert`，必须先删后插 | `DefaultKbIndexingService` 的类注释 |
| 向量化整批 400 `batch size is invalid` | DashScope 文本 embedding 一次最多 10 条 | `ai.rag.kb.embedding.batch-size` |
| 重排回 403 `AccessDenied` | 那把 key 没开通 `gte-rerank`，开通的是 `gte-rerank-v2` | `ai.rag.kb.rerank.model` 默认值 |
| 集合建了但写入报 `collection not found` | `build()` 不调 `afterPropertiesSet()`，自己 new 的实例必须显式调 | `KbVectorStoreFactory#createCollection` |
| 翻一个 `enabled` 位像是要重算向量 | Milvus 没有局部更新，`upsert` 也是整行写 → `enabled` 只存库里、检索后过滤 | `db/knowledge-schema.sql` 头注 |
