# 向量库环境实测记录（2026-09-15）

> 这份文档回答一个问题：**"本地 PG + pgvector"这条路在本机为什么没走通，走了哪条替代路，以及换回来要改什么。**
>
> 它存在的理由是：环境阻塞最容易被记成一句"没装成"，然后下次再撞一遍。
> 这里把**每一条都写成可复现的验证命令 + 实测输出**，并且明确写出
> **"因此哪些结论不能下"** —— 后者比前者更重要。

---

## 一、三条路都试过了（附命令与实测结果）

| # | 方案 | 实测命令 | 实测结果 | 结论 |
|---|---|---|---|---|
| 1 | Docker Desktop 起容器 | `docker info` / `docker version` | 引擎报 **`failed to start`**，`docker context ls` 有 `desktop-linux` 但管道 `//./pipe/docker_engine` 不存在 | ❌ |
| 1b | 同上（看原因） | 读 `%LOCALAPPDATA%\Docker\log\host\electron-*.log` | 日志原文：`updateStatus: 'OsNotSupported'` | ❌ 明确不支持 |
| 2 | 本机已装 PostgreSQL | `psql --version`；`Get-NetTCPConnection -LocalPort 5432`；`Test-Path "C:\Program Files\PostgreSQL"` | 命令不存在；无监听；目录不存在 | ❌ 没装 |
| 3 | 源码编译 pgvector | `Get-ChildItem -Recurse -Filter cl.exe` / `nmake.exe` / `Test-Path "…\Windows Kits\10\Include"` | 三个都没有（VS 目录只有空壳，Chocolatey 装了 `visualstudio2026buildtools` 但没有 MSVC 工具链） | ❌ 没有编译器 |

### 关于第 1 条的细节（值得记下来）

- `docker --version` **成功**返回 `Docker version 20.10.17` —— 但那只是 CLI，
  它不代表引擎能用。**"CLI 能跑"和"守护进程在跑"是两件事**，
  判断依据必须是 `docker version` 里有没有 `Server:` 段，或 `docker info` 能不能通。
- Docker Desktop 服务 `com.docker.service` 是 `Running` 的（Windows 服务），
  但引擎要的是 **WSL2 后端**，而本机 OS 是
  **Windows 10 家庭中文版 10.0.18363（1909）**——Docker Desktop 当前版本已不支持它，
  所以 Electron 前端一起来就自己退出了（`Docker Desktop is quitting, destroying Whale icon`）。
- 系统里有 `Ubuntu-20.04` 的 WSL1 发行版可用，但 **Docker Desktop 要的是 WSL2 + 内核**，
  而 WSL2 需要 19041+，本机 18363 达不到。

> **通用教训**：排查"容器起不来"时，**先看日志里的状态字**（这里是 `OsNotSupported`），
> 再决定要不要折腾。我在"重启服务、重开进程、等 180 秒"上花掉了十几分钟，
> 而日志里一行就写明了原因 —— 而这个原因**不是你重启能解决的**。

## 二、还撞上了第二个封锁：供应商没有 Embedding 端点

这一条与向量库无关，但同样致命 —— **没有 embedding 就算有 pgvector 也没用**。

| 验证 | 命令 | 实测结果 |
|---|---|---|
| 有哪些模型 | `GET https://api.deepseek.com/v1/models` | 只有 `deepseek-flash`、`deepseek-v4-pro` |
| 有没有 embedding | `POST /v1/embeddings`、`POST /embeddings`（试了 `deepseek-embedding`、`deepseek-v4-embedding`） | **一律 404** |

也就是说：本项目当前唯一的模型供应商**在协议上就没有这个能力**，
而 API Key 只有这一个（换供应商 = 换 key = 用户的决定，不是实现能自己解决的）。

## 三、于是选了什么路，以及这条路的边界

**选的路**：把不依赖环境的那部分做完，并把缺的部分做成**可替换的接口**。

| 缺的东西 | 本轮的替代 | 换回真东西要改哪里 |
|---|---|---|
| PG + pgvector | 自己写的 `VectorIndex`（暴力精确 KNN + 余弦相似度） | **只改 `VectorIndex` 一个文件**：`add` 变成写表、`search` 变成一条 `ORDER BY embedding <=> ?` 的 SQL |
| 真 Embedding 模型 | `HashingEmbeddingModel`（本地哈希 + IDF 加权，离线可复现） | **只换 `EmbeddingModel` 的实现**（它实现的是 **Spring AI 的** `org.springframework.ai.embedding.EmbeddingModel` 接口，不是自定义接口）；下游评测、诊断、界面一行不用改 |

这样做的理由不是"绕过困难"，而是：**检索侧要学的东西没有一条依赖具体是哪个模型算的向量**——
向量化 → 建索引 → 相似度检索 → 与词法检索对照 → 等 token 预算比较，这五步全都与模型无关。

### ⚠️ 因此**不能**下的结论（这一节比上面所有内容都重要）

当前向量那一路（`local-hash-idf`）**不是语义嵌入**，它是"哈希技巧 + TF-IDF"的稠密版本，
**仍然建立在词面重合上**。它能跨过的只是"同一个词以不同密度出现"，
**跨不过**"提问说『内存泄漏』、文档写『OOM』"这类真正的词汇不匹配 ——
而那恰恰是向量检索最值钱的场景。

所以：

- ✅ **能说**：「换一种度量方式（词法 → 稠密向量 → 两路融合）之后，**分块策略的结论变了没有**」——
  因为这里比的是**同一种度量下的两种分块**，度量本身的强弱不影响这个比较。
- ❌ **不能说**：「向量检索比 BM25 强 / 弱」「混合检索提升了多少」——
  换一个真 embedding 模型，这两路的数字会**完全不一样**。
- ❌ **不能说**：「本项目验证了 pgvector / VectorStore 的生产用法」——
  生产用法（HNSW/IVF 索引、批量写入、事务、权限预过滤）一条都没碰到。

这三条已经同步写进了 `AlignmentExperiment.notes()`，会随接口一起返回给界面 ——
**结论的边界必须跟数字一起出现**，否则读者只会看到"混合检索 Recall 多少"然后自行脑补。

## 四、将来回到"本地 PG + pgvector"时要做的事

按投入从低到高：

1. **升级 OS 到 Windows 10 2004+（19041+）**，装 WSL2 内核 → Docker Desktop 可用。
   这是最省事的一条，但需要重启与管理员权限。
2. 或者**装一个本机 PostgreSQL**（EDB 安装包），再单独编译 pgvector 扩展
   （需要 MSVC + Windows SDK）。
3. 或者用 `io.zonky.test:embedded-postgres`（Java 内嵌 PG），
   仍然需要自行把 pgvector 的 `vector.dll` / SQL 脚本放进 PG 的扩展目录。

接上之后的**第一步不是写代码，而是量一遍**：
把同一个 `embeddingModel` 实现换成真模型，跑 `/api/diag/rag/align`，
对比 `local-hash-idf` 与真模型下的 Recall/MRR。
**这两组数字的差距本身就是一份材料**（"离线近似品能把结论带到多接近"）。

## 五、附带确认的一件事：Spring AI 2.0.1 的 EmbeddingModel 契约

本机没有 `VectorStore` 所在的 artifact（`spring-ai-vector-store` / `spring-ai-rag` 都不在本地仓库，
`pgvector` 也没有），但**`EmbeddingModel` 接口在 `spring-ai-model` 里**，
所以实现是**照着真接口写的**（`javap` 实测）：

```java
public interface org.springframework.ai.embedding.EmbeddingModel
        extends org.springframework.ai.model.Model<EmbeddingRequest, EmbeddingResponse> {
  EmbeddingResponse call(EmbeddingRequest);   // 抽象，必须实现
  float[] embed(String);                      // default
  float[] embed(Document);                    // 抽象，必须实现
  List<float[]> embed(List<String>);          // default
  int dimensions();                           // default
}
```

也就是说：`HashingEmbeddingModel` 不是"自成一派的假接口"，
它**可以直接被换成 `OpenAiEmbeddingModel` / `OllamaEmbeddingModel`**，
而向量那一路的代码不需要任何适配 —— 这正是"面向接口编程"在这个项目里的实际兑现。
