# 向量库环境实测记录（2026-09-15）

> 这份文档回答一个问题：**"本地 PG + pgvector"这条路在本机为什么没走通，走了哪条替代路，以及换回来要改什么。**
>
> 它存在的理由是：环境阻塞最容易被记成一句"没装成"，然后下次再撞一遍。
> 这里把**每一条都写成可复现的验证命令 + 实测输出**，并且明确写出
> **"因此哪些结论不能下"** —— 后者比前者更重要。

---

## 〇、先看这张表：RAG 到底需要什么环境（**分三档，不要混着看**）

结论先说：**RAG 本地实验台不需要任何外部环境**。这一轮的整套对照评测、向量与混合检索，
全都是在"无数据库、无 embedding 模型、0 次调模型"下跑出来的
（这些数字现在可以用诊断端点随时重新量，见下面的复现命令）。
所以"RAG 要准备什么"这个问题必须先分清是**哪一档**：

| 档位 | 要准备什么 | 现在状态 | 卡在哪 |
|---|---|---|---|
| **① 跑本模块（含向量 + 混合检索）** | **JDK 21 + Maven** | ✅ **已具备** | 什么都不缺 |
| **② 出"真向量"的数字** | 一个**提供 embedding 的 OpenAI 兼容端点**：key + base-url + 模型名 + 向量维度 | ❌ 缺 | **DeepSeek 没有 embedding 端点**（见第二节实测） |
| **③ 生产形态** | **独立向量库**（Milvus）／ **PG + pgvector** + 离线管道 | 🟢 **向量库已在用** | 知识库那条链路已经跑在 Milvus 上（一个库一个集合，真 DashScope 向量，第六节）；PG + pgvector 三条路仍堵着（第一节） |

### ① 为什么"什么都不缺"（依赖清单，可核对）

| 用途 | 依赖 | 需要外部服务吗 |
|---|---|---|
| 文档解析 | `tika-core` + `tika-parsers-standard-package` 3.3.2、`flexmark-all` 0.64.8 | ❌ 纯本地 |
| 词法检索 | `lucene-core` / `analysis-common` / `queryparser` 10.5.1（**内存索引** `ByteBuffersDirectory`） | ❌ 不起服务、不落盘 |
| 向量检索 | `HashingEmbeddingModel`（哈希 + IDF，纯计算）+ `VectorIndex`（暴力 KNN） | ❌ **不调模型、不连库** |
| 语料 + 评测集 | `src/main/resources/rag/corpus/*.md`（4 份，84200 字符）+ `eval-set.tsv`（43 条） | ❌ 随包发布 |

复现命令（**不依赖测试**：只编译，然后起服务打诊断端点）：

```bash
cd ai-agent
mvn -o compile                               # 离线编译，完全不联网（-o）
run.cmd                                      # 起服务（验 RAG 给个假 key 即可）

# 数字用诊断端点重新量（不需要 API Key、不调模型）
curl "http://127.0.0.1:8080/api/diag/rag/corpus"    # 语料解析概览 + 块类型分布
curl "http://127.0.0.1:8080/api/diag/rag/compare"   # 两种策略并排对照（秒级）
curl "http://127.0.0.1:8080/api/diag/rag/align"     # 块大小对齐实验（更重，给足超时）
```

> ⚠️ 这里原先写的是 `mvn -o test`（当时 102 个测试，其中一个评测报告类会打印可整段引用的对照表）——
> 那批后端测试已在 2026-09-18 整体删除，`rag-baseline.json` 也没了。
> **现在没有任何自动化在比对数字**：本文档里的实测数字要重新量，
> 只能拿上面几个端点的输出自己与本文档对照。

**两个容易踩的点**（都与 RAG 无关，但会让人误以为 RAG 需要环境）：

1. **跑整个应用必须给 `OPENAI_API_KEY`** —— 是 `ApiKeyStartupCheck` 在 `@PostConstruct` 里拦
   （Key 没读到就拒绝启动）。RAG 的端点是纯离线的，只是和聊天接口住在同一个进程里。
   只想验证 RAG：`--spring.ai.openai.api-key=test-key` 就能起。
2. **`ai.rag.vector.*` 有代码默认值但配置文件里没写**（维度 512、每词项落 3 维、分数阈值 0）。
   不写也能跑；要调参再往 `application.properties` 里加。

### ② 想接真 embedding：**一个 key 就够，这是性价比最高的一条**

需要的是：一个**提供 embedding 模型**的 OpenAI 兼容端点（百川 / 阿里 / OpenAI / 本地 Ollama 都行），
以及它的 key、base-url、模型名、向量维度。

**为什么必须换**：现在用的 `local-hash-idf` 是"哈希 + TF-IDF"的稠密版本，
仍然建立在**词面重合**上，跨不过"提问说内存泄漏、文档写 OOM" ——
而那恰恰是向量检索最值钱的场景。

**换的代价很小**：`HashingEmbeddingModel` 实现的是 Spring AI 的真接口
（`javap` 核过 2.0.0 契约），替换实现类即可，下游零改动。
**但有一条不能忘**：换模型必须**全量重建索引**（两个向量空间不可比，混用不报错、只是排序变成随机的）。
这条已经做成代码：`VectorIndex` 存索引指纹，维度对不上**直接抛**。

**拿到 key 之后第一件事不是写代码，是量一遍**：同一份语料跑 `/api/diag/rag/align`，
对比 `local-hash-idf` 与真模型的 Recall/MRR。**这两组数字的差距本身就是材料**
（"离线近似品能把结论带到多接近"）。

### ③ 生产形态：向量库这一块已具备（Milvus），PG + pgvector 三条路仍堵着

Milvus standalone 已装好并在本机运行，装法与踩过的点见**第六节**。下面第一节记录的
Docker / 本机 PostgreSQL / 源码编译 pgvector 三条路的实测，说的是 **PG + pgvector** 那一条。

真正需要它的是**另一类知识**，而不是性能 ——
这批语料 516 个块，暴力 KNN 是毫秒级。上 PG + pgvector 换来的东西是：
HNSW/IVF 索引调参、维度上限（pgvector `vector` 类型 2000 维）、`<=>` 算子、
批量写入与事务、以及**权限预过滤要用到的元数据列**。

| 1b | 同上（看原因） | 读 `%LOCALAPPDATA%\Docker\log\host\electron-*.log` | 日志原文：`updateStatus: 'OsNotSupported'` | ❌ 明确不支持 |

### 关于第 1 条的细节（值得记下来）

- `docker --version` **成功**返回 `Docker version 20.10.17` —— 但那只是 CLI，
  它不代表引擎能用。**"CLI 能跑"和"守护进程在跑"是两件事**，
  判断依据必须是 `docker version` 里有没有 `Server:` 段，或 `docker info` 能不能通。
- Docker Desktop 服务 `com.docker.service` 是 `Running` 的（Windows 服务），
  但引擎要的是 **WSL2 后端**，而本机 OS 是
  **Windows 10 家庭中文版 10.0.18363（1909）**——Docker Desktop 当前版本已不支持它，
  所以 Electron 前端一起来就自己退出了（`Docker Desktop is quitting, destroying Whale icon`）。
- 系统里有 `Ubuntu-20.04` 的 WSL1 发行版可用，但 **Docker Desktop 要的是 WSL2 + 内核**，
  而 WSL2 需要 19041+，本机 18363 达不到。

> **通用教训**：排查"容器起不来"时，**先看日志里的状态字**（这里是 `OsNotSupported`），
> 再决定要不要折腾。我在"重启服务、重开进程、等 180 秒"上花掉了十几分钟，
> 而日志里一行就写明了原因 —— 而这个原因**不是你重启能解决的**。

## 二、还撞上了第二个封锁：供应商没有 Embedding 端点

这一条与向量库无关，但同样致命 —— **没有 embedding 就算有 pgvector 也没用**。

| 验证 | 命令 | 实测结果 |
|---|---|---|
| 有哪些模型 | `GET https://api.deepseek.com/v1/models` | 只有 `deepseek-flash`、`deepseek-v4-pro` |
| 有没有 embedding | `POST /v1/embeddings`、`POST /embeddings`（试了 `deepseek-embedding`、`deepseek-v4-embedding`） | **一律 404** |

也就是说：本项目当前唯一的模型供应商**在协议上就没有这个能力**，
而 API Key 只有这一个（换供应商 = 换 key = 用户的决定，不是实现能自己解决的）。

## 三、于是选了什么路，以及这条路的边界

**选的路**：把不依赖环境的那部分做完，并把缺的部分做成**可替换的接口**。

| 缺的东西 | 本轮的替代 | 换回真东西要改哪里 |
|---|---|---|
| PG + pgvector | 自己写的 `VectorIndex`（暴力精确 KNN + 余弦相似度） | **只改 `VectorIndex` 一个文件**：`add` 变成写表、`search` 变成一条 `ORDER BY embedding <=> ?` 的 SQL |
| 真 Embedding 模型 | `HashingEmbeddingModel`（本地哈希 + IDF 加权，离线可复现） | **只换 `EmbeddingModel` 的实现**（它实现的是 **Spring AI 的** `org.springframework.ai.embedding.EmbeddingModel` 接口，不是自定义接口）；下游评测、诊断、界面一行不用改 |

这样做的理由不是"绕过困难"，而是：**检索侧要学的东西没有一条依赖具体是哪个模型算的向量**——
向量化 → 建索引 → 相似度检索 → 与词法检索对照 → 等 token 预算比较，这五步全都与模型无关。

### ⚠️ 因此**不能**下的结论（这一节比上面所有内容都重要）

当前向量那一路（`local-hash-idf`）**不是语义嵌入**，它是"哈希技巧 + TF-IDF"的稠密版本，
**仍然建立在词面重合上**。它能跨过的只是"同一个词以不同密度出现"，
**跨不过**"提问说『内存泄漏』、文档写『OOM』"这类真正的词汇不匹配 ——
而那恰恰是向量检索最值钱的场景。

所以：

- ✅ **能说**：「换一种度量方式（词法 → 稠密向量 → 两路融合）之后，**分块策略的结论变了没有**」——
  因为这里比的是**同一种度量下的两种分块**，度量本身的强弱不影响这个比较。
- ❌ **不能说**：「向量检索比 BM25 强 / 弱」「混合检索提升了多少」——
  换一个真 embedding 模型，这两路的数字会**完全不一样**。
- ❌ **不能说**：「本项目验证了 pgvector / VectorStore 的生产用法」——
  生产用法（HNSW/IVF 索引、批量写入、事务、权限预过滤）一条都没碰到。

这三条已经同步写进了 `AlignmentExperiment.notes()`，会随接口一起返回给界面 ——
**结论的边界必须跟数字一起出现**，否则读者只会看到"混合检索 Recall 多少"然后自行脑补。

## 四、将来回到"本地 PG + pgvector"时要做的事

按投入从低到高：

1. **升级 OS 到 Windows 10 2004+（19041+）**，装 WSL2 内核 → Docker Desktop 可用。
   这是最省事的一条，但需要重启与管理员权限。
2. 或者**装一个本机 PostgreSQL**（EDB 安装包），再单独编译 pgvector 扩展
   （需要 MSVC + Windows SDK）。
3. 或者用 `io.zonky.test:embedded-postgres`（Java 内嵌 PG），
   仍然需要自行把 pgvector 的 `vector.dll` / SQL 脚本放进 PG 的扩展目录。

接上之后的**第一步不是写代码，而是量一遍**：
把同一个 `embeddingModel` 实现换成真模型，跑 `/api/diag/rag/align`，
对比 `local-hash-idf` 与真模型下的 Recall/MRR。
**这两组数字的差距本身就是一份材料**（"离线近似品能把结论带到多接近"）。

## 五、附带确认的一件事：Spring AI 2.0.0 的 EmbeddingModel 契约

本机没有 `VectorStore` 所在的 artifact（`spring-ai-vector-store` / `spring-ai-rag` 都不在本地仓库，
`pgvector` 也没有），但**`EmbeddingModel` 接口在 `spring-ai-model` 里**，
所以实现是**照着真接口写的**（`javap` 实测）：

```java
public interface org.springframework.ai.embedding.EmbeddingModel
        extends org.springframework.ai.model.Model<EmbeddingRequest, EmbeddingResponse> {
  EmbeddingResponse call(EmbeddingRequest);   // 抽象，必须实现
  float[] embed(String);                      // default
  float[] embed(Document);                    // 抽象，必须实现
  List<float[]> embed(List<String>);          // default
  int dimensions();                           // default
}
```

也就是说：`HashingEmbeddingModel` 不是"自成一派的假接口"，
它**可以直接被换成 `OpenAiEmbeddingModel` / `OllamaEmbeddingModel`**，
而向量那一路的代码不需要任何适配 —— 这正是"面向接口编程"在这个项目里的实际兑现。

## 六、Milvus：已经在本机跑起来了（2026-10-16）

### 现状

| 项 | 值 |
|---|---|
| 服务 | Milvus standalone **2.6.0**（官方 DEB 包里的原生二进制 `milvus run standalone`） |
| 位置 | WSL1 发行版 `Ubuntu-20.04` 里，`/home/ljf/milvus/` |
| 端口 | `127.0.0.1:19530`（gRPC，应用连这个）；`9091`（管理面 / WebUI） |
| 存储 | **嵌入式 etcd + `common.storageType=local`** —— 不需要另起 etcd / MinIO |
| Milvus 数据 | `/home/ljf/milvus/data/`（`milvus.yaml` 里 `/var/lib/milvus` 已被改写到这） |
| etcd 数据 | `/home/ljf/milvus/default.etcd/`（**位置由启动时的 cwd 决定**，见下面第 5 点） |

WSL1 与 Windows **共用网络栈**，所以 Windows 侧的 `localhost:19530` 直接可连
（实测 `Test-NetConnection localhost 19530` → `TcpTestSucceeded=True`，
`127.0.0.1` 与 WSL 网卡地址 `192.168.193.1` 三个地址都通）。

**版本为什么是 2.6.0 而不是最新的 3.x**：客户端不在 pom 里单独钉，它来自 Spring AI BOM ——
`spring-ai-bom:2.0.0` 带的是 `io.milvus:milvus-sdk-java:2.5.8`（`mvn dependency:list` 实测），
所以服务端 2.6.0 与它同一大版本线，差一个小版本。
另外查过 GitHub Release 的资产：`v2.5.0` / `v2.6.21` / `v2.6.25` / `v3.0.0` / `v3.0.2` / `v3.0.3`
**都只挂了 docker-compose yaml**，deb/rpm 只有 `v2.4.1` 与 `v2.6.0` 两版有。

### 为什么不走官方首选的 Docker

官方 Windows 安装页（`getstarted/run-milvus-docker/install_standalone-windows.md`）要求
**Docker Desktop + WSL 2 + 管理员模式**，本机三条都不成立：

| 检查项 | 命令 | 实测结果 |
|---|---|---|
| Docker 引擎 | `docker info` | `failed to start`；日志原文 `LinuxWSL2Engine sent docker state failed to start` |
| WSL2 | `wsl -d docker-desktop-data -- echo hi` | 「请启用虚拟机平台 Windows 功能并确保在 BIOS 中启用虚拟化」 |
| 虚拟化硬件 | `Win32_Processor.VirtualizationFirmwareEnabled` | `True`（BIOS 这侧是开的，卡在 Windows 功能/ hypervisor） |
| 可选功能 | `Win32_OptionalFeature` | `VirtualMachinePlatform` / `HypervisorPlatform` 均 `InstallState=1`（已启用），但 `HypervisorPresent=False` |
| 管理员 | `[Security.Principal.WindowsPrincipal]…IsInRole(Administrator)` | `False` |

即：**要修好得由人用管理员权限启用「虚拟机平台」并重启**，当前会话做不到。

官方文档里还有一条 **RPM/DEB 包**路径
（`getstarted/run-milvus-docker/install_standalone-binary.md`，该页**没有** deprecated 标记），
装出来是 `/usr/bin/milvus` + `/usr/lib/milvus/`，
**不依赖 Docker、不需要 root**（用 `dpkg-deb -x` 解包到用户目录），所以走了这条。

> 另一条官方非 Docker 路径 **Milvus Lite 用不了**：官方对照表写明它的 SDK 只有
> **Python**，`MilvusClient("./x.db")` 是**进程内嵌**的，没有对外 gRPC 端口，
> Java 侧的 `MilvusVectorStore` 连不上。

### 怎么装 / 怎么启停

```bash
# 安装（在 WSL 里跑；下载 191MB 的 deb 并解包到 ~/milvus）
wsl -d Ubuntu-20.04 -- bash "/mnt/c/Users/ljf/Desktop/ai agent/scripts/milvus-install-wsl.sh"
```

```powershell
# 启停（Windows 侧）
pwsh -File scripts/milvus-start.ps1     # 等到 healthz 200 才返回
pwsh -File scripts/milvus-stop.ps1
```

**每次 Windows 重启（或 `wsl --shutdown`）之后 Milvus 不会自己起来**，要重跑 `milvus-start.ps1`。

### 六个已经踩过的点

1. **WSL1 没有 systemd**，DEB 里的 `milvus.service` 起不来（`ExecStart=/usr/bin/milvus run standalone`）。
   只能把二进制当前台进程跑，并由一个**独立的 `wsl.exe` 进程**兜住 —— 一旦那个 WSL 会话结束，
   WSL1 会把 Milvus 一起收掉（实测：日志出现 `handleSignals goroutine quit` 后进程消失）。
   `milvus-start.ps1` 用 `Start-Process` 起独立进程，就是为了这个。
2. **就绪判据要用 `http://127.0.0.1:9091/healthz` 返回 200，不能只看端口通**。
   实测刚启动时 19530 已经接受连接、v2 API 也能应答，但 `healthz` 还是 500。
3. **DEB 里的 `libquadmath.so` 是个断链**（指向自己没带的 `libquadmath.so.0`），
   它把 `libquadmath0` 声明成外部依赖。系统里没有时 `ldd` 报
   `libquadmath.so.0 => not found`，必须从 Ubuntu 归档补一个（安装脚本里做了）。
4. **`milvus.yaml` 默认写 `/var/lib/milvus`、读 `/etc/milvus/configs`，两处都要 root**。
   安装脚本把整份配置复制到 `~/milvus/conf` 并把这两个前缀改写掉。
5. **嵌入式 etcd 的数据目录只能由启动时的 cwd 决定，配置指定不了**。
   实测两处都设过 —— `embedEtcd.yaml` 的 `data-dir`、`milvus.yaml` 的 `etcd.data.data.dir` ——
   etcd 日志里仍然是 `"data-dir":"default.etcd"`（相对路径），因为 Milvus 是用命令行
   `--data-dir` 起它的，覆盖了配置文件。而 `wsl.exe` 会把 **Windows 侧的工作目录**
   （就是本仓库根）当 cwd 带进来，于是 60MB+ 的 etcd 数据一度直接落进了仓库目录。
   约束在启动脚本的 `cd "$BASE"` 里，所以 etcd 数据固定在 `~/milvus/default.etcd`。
6. **停止时日志末尾会跟一条 `panic: context canceled` 堆栈**。
   它出现在 `All cleanup done, handleSignals goroutine quit` **之后** ——
   清理已经做完，这条是退出路径上的现象，不代表数据有问题。

两个不写就会启动失败的键：

- `spring.ai.model.embedding=none` —— OpenAI starter 的 `OpenAiEmbeddingAutoConfiguration`
  也是 `matchIfMissing=true`，会和项目自己的 `HashingEmbeddingModel` 撞成两个 `EmbeddingModel`，
  Milvus 那边按类型注入直接失败（实测：`expected single matching bean but found 2:
  hashingEmbeddingModel, openAiEmbeddingModel`）。与 `spring.ai.model.chat=openai` 是同一类问题。
- `spring.ai.vectorstore.milvus.embedding-dimension` 必须是 **512**（= `ai.rag.vector.hash.dimensions`），
  本键默认值是 1536；不对齐时建出的集合维度与写入的向量不符。
  ⚠️ 这一条只约束**自动装配那个** `vector_store` 集合；知识库的集合各自按
  `knowledge_base.embedding_dim` 建（默认 1024，来自 DashScope），两者互不影响。

**已实测到的效果**：应用启动后 Milvus 里出现集合 `vector_store`
（`FloatVector` 维度 **512**、`metricType=COSINE`、`LoadStateLoaded`），
重复启动不会再建（内部先 `hasCollection`）。

### 本项目到底用哪个集合（2026-10-17 起）

| 链路 | 用的东西 | 集合 |
|---|---|---|
| 阶段二 · 离线评测（解析/分块/三路检索/评测集） | 进程内 `VectorIndex`（暴力精确 KNN，`HashingEmbeddingModel` 512 维） | 不用 Milvus |
| 知识库（上传文档 → 检索 → 对话注入） | 每个知识库一个 `MilvusVectorStore`，由 `KbVectorStoreFactory` 现场构造 | `{ai.rag.kb.collection-prefix}{kbId}`，维度来自该库建库时的 embedding 快照 |
| 自动装配那一个 | `MilvusVectorStore`（Spring 建的 Bean） | `vector_store`，**不参与任何业务链路**，只作为"连得上、能建集合"的自检与手工试连入口 |

**★ 一个必须写下来的坑：`MilvusVectorStore.Builder.build()` 不建集合**

字节码核过：`build()` 只做 `new MilvusVectorStore(builder)`，建集合发生在
`afterPropertiesSet()` 里。自动装配那个 Bean 之所以能建出集合，是 Spring 按 `InitializingBean`
替它调的；自己 `new` 出来的实例（知识库就是这么干的）**必须显式调一次**
`store.afterPropertiesSet()` —— 不调的话集合永远不存在，而报错出现在很久之后
第一次 `add()` 上（`collection not found`），离原因很远。

### ⚠️ 因此**不能**下的结论

- **阶段二那条评测链路仍然不用 Milvus**：`VectorIndex` 还是本地暴力精确 KNN，
  `Retriever` 契约与 `VectorIndex#search` 那道接缝没动过 —— 评测里那些数字的边界（本文档第三节）
  一条都没变。
- **知识库那条链路**用的是真 Milvus + DashScope 真向量，但它**没有跑过规模**：
  最大的一份文档是 24KB 切 30 块（实测）。所以 HNSW/IVF 索引调参、大集合下的召回率、
  并发写入、跨进程互斥这些**生产问题一个都还没验证过** —— 现在这个规模上它们不会暴露。
