## 这一阶段要回答的问题

不是「RAG 能不能跑通」（那个半天就能跑通），而是路线文档规定的验收口径：

> **能用数字说明「换分块策略 / 加 Rerank 提升了多少」，而不是「好像变好了」。**

所以本模块的形态与阶段一不同：阶段一是在线链路（一次请求怎么发），
这里是**离线实验台** —— 同一份语料、同一套评测集、同一个检索器，
只换分块策略各跑一遍，把指标并排摆出来。

## 环境前提（**这一节单独列出来，因为它决定了"能不能跑"**）

分三档，**当前代码只依赖第 ① 档**：

| 档位 | 需要什么 | 说明 |
|---|---|---|
| **① 跑本模块（含向量与混合检索）** | **JDK 21 + Maven** | RAG 相关依赖全是内嵌库（Tika / flexmark / Lucene 内存索引 / 自研向量索引），**不需要数据库、不需要 embedding 模型、评测过程 0 次调模型** |
| **② 出"真向量"的数字** | 一个**提供 embedding 的 OpenAI 兼容端点**（key + base-url + 模型名 + 维度） | ❌ 当前缺：DeepSeek 没有 embedding 端点。替代品 `local-hash-idf` 是"哈希 + TF-IDF"，**不是语义嵌入** |
| **③ 生产形态** | **PG + pgvector** 或独立向量库 + 离线管道 | ❌ 本机三条路都被封，命令与实测见 `向量库环境记录.md` |

**两个容易踩的点**：

- 跑**整个应用**（`mvn spring-boot:run`）必须给 `OPENAI_API_KEY`，但这**与 RAG 无关** ——
  是 `ApiKeyStartupCheck` 在 `@PostConstruct` 里拦（Key 没读到就拒绝启动）。
  只想验证 RAG 时给假 key 即可：`--spring.ai.openai.api-key=test-key`（测试里就是这么做的）。
- `ai.rag.vector.*` **有代码默认值（维度 512、每词项落 3 维、阈值 0）但配置文件里没写** ——
  想调它再往 `application.properties` 加，不写也能跑。

服务起来之后（`run.cmd`）用诊断端点：

| 端点 | 作用 |
|---|---|
| `GET /api/diag/rag/corpus` | 语料解析概览 + **块类型分布** |
| `GET /api/diag/rag/preview?strategy=structural&detail=5` | 直接看块长什么样 |
| `GET /api/diag/rag/tokens?text=...` | 一段文本被切成哪些 tokens |
| `GET /api/diag/rag/retrieve?query=...&strategy=structural` | 单条提问的召回与名次 |
| `GET /api/diag/rag/eval-set` | 评测集条数与分组 |
| `GET /api/diag/rag/compare` | 两种策略并排对照（**原始对照，不能用来判断"哪个策略更好"**） |
| `GET /api/diag/rag/align` | **核心：块大小对齐实验**（两个轴 × 三路检索）。比 `/compare` 重约 4 倍，前端要单独给超时（建议 180s） |

**排查顺序建议**：`corpus` → `preview` → `tokens` → `retrieve` → `compare`。
解析不对，后面全是白费功夫；所以先看块类型分布里 `heading` 是不是 0。

**要判断"分块策略本身好不好"，看 `/align` 而不是 `/compare`** ——
后者两组的块大小不同，而判定标准是"块有没有覆盖答案所在章节"（块越大越容易覆盖），
所以它的差值**不可归因**。详见下面两节。

|---|---|---|---|---|---|---|

## 结论（**改写后的版本**）

**1. 对齐块大小之后，"结构分块省 token"这个优势消失了。**
全语料 token **36899 vs 39204**、重复率 **13.82% vs 20.93%**、前 3 条候选 token **644 vs 629**。
原先它整体更省，只是因为**它的块更小**（同样内容切成更多块、每块分摊的固定开销被摊薄），
不是切法本身更高效。这就是"两个轴必须一起看"的意义。

**2. 在平均块大小相同的前提下，这份语料 + 这三个检索器上，固定字数硬切全面占优。**
Recall@5 / Recall@1 / MRR / token 成本 / 重复率五项全优，且三路检索方向一致。
**这条必须原样保留** —— 不能因为"结构分块是我做的"就把它写轻。

**3. 词法检索会放大分块缺陷，向量会掩埋它。**
同一处分块差异，词法下 ΔMRR 是 **−11.03pp**，向量下只有 **−5.43pp**。
这解释了为什么很多团队在 BM25 下调不好分块、换成向量就"看起来好了" ——
**不是分块变好了，是度量变宽容了**。

**4. 不能从这份报告推出的结论。**

- ❌ **"语义分块是错的"** —— 本项目的"结构分块"只做了三件事（标题层级 + 段落边界 + 面包屑），
  **没做**语义相似度分块、父子块（small-to-big）、表格/代码专门处理。
  它在这份语料上的表现只说明**这三个机制没换来收益**。
- ❌ **"块越大越好"** —— 判定标准天然奖励大块，所以必须同时看等预算那一轴：
  1000 预算内两组装进来 4.2 vs 4.3 条（几乎一样），而 Recall 是 0.7907 vs 0.7209。
- ❌ **"向量检索比 BM25 强/弱"** —— 向量那一路是离线近似品，数字评价的是近似品。
- ✅ 能说的是：**在这份语料、这个相关性判定口径、这三种检索方式下，按固定字数切更划算。**

## 为什么结论会改（留个轨迹，这比结论本身有用）

第一版报告写的是「结构分块没有提升召回率，但省 token」，并明确留了一句
"不能说它更好或更差，因为块大小这个混杂因素没排除"。
第二轮把这个混杂因素排除之后，**"省 token"这一半也站不住了** ——
它和"召回略低"是同一个原因（块更小），而不是一个收益。

**这次修订本身就是验收口径想要的东西**：先有一句能被追问的话
（"提升了多少"），再自己去追问它（"这个对照可信吗"），
然后**接受"我做的那个方案没赢"这个结果并写进文档**。

## 已知局限（都写在这里，免得被当成结论引用）

| 局限 | 说明 |
|---|---|
| **向量那一路不是语义嵌入** | `local-hash-idf` 是"哈希 + TF-IDF"，仍建立在**词面重合**上，跨不过"提问说内存泄漏、文档写 OOM"。所以它能支撑的只有「换了度量方式之后分块结论变了吗」，**不能**支撑「向量检索比 BM25 强多少」。换真模型要全量重建索引（`VectorIndex` 有指纹校验，维度不一致直接抛） |
| **真向量库未接** | PG + pgvector 在本机三条路都被封（Docker `OsNotSupported` / 无本机 PG / 无 MSVC），详见 `向量库环境记录.md`。HNSW/IVF 索引、批量写入、事务、并发这些生产问题**一个都没验证过** |
| **对照仍是"另一种硬切"** | 对齐了**平均块大小**（差 0.39 token），但没有对齐**块数**与**全语料 token**（那两项由切法决定，无法用硬切同时按住）。结论的边界是：这份语料 + 这个判定口径 + 这三种检索方式 |
| **判定口径天然奖励大块** | 判定是"块是否覆盖答案所在章节"。所以等预算那一轴不是可选项，是必须一起看的第二条轴 |
| **只有 4 份文档、43 条用例** | 够用（路线文档要求 30–50 条），但换一批文档结论可能不同 |
| **权限预过滤未做** | 路线文档里的「先检索再过滤 = 静默召回缺失」这一条还没实现，属于下一步 |
| **Rerank 未做** | 现在 topK 固定 10，还没有「粗召回 30–100 → Rerank 后 5–10 → 进上下文 3–6」的分层 |
| **`/align` 还没接界面** | 后端端点、实验、证据、断言都齐了，界面还是空白（下一步第一件事） |

## 这个模块踩过的坑（都写进了代码注释）

1. **Tika 把 `.md` 当纯文本** —— 13KB 带 19 个标题的文档被解析成 1 个 `<p>`，
   "按标题层级分块"根本没发生，且不报任何错。→ 必须走 flexmark 转 HTML。
2. **flexmark 扩展要同时注册到 Parser 与 HtmlRenderer** —— 只注册 Parser 时
   AST 里明明有 `TableBlock`，渲染出来却一个 `<table>` 都没有。
3. **`Group.of` 里 `start = 0` 当初始值** —— `Math.min(0, x)` 恒为 0，
   于是每个块的面包屑都退化成文档 H1，相关性判定全灭、Recall 恒为 0。
4. **相关性判定不能用"块的标题路径"** —— 对照组没有标题路径，
   会被恒判为不相关，Recall 被压成 0.00（一个朝有利方向偏的假结论）。
5. **`maxTokens` 被绕过三次** —— 合并漏算面包屑（802 token 的块）、
   拆分重新估算丢了面包屑（410/411）、`block.order()` 与标题路径下标不是同一坐标系。
   → 最终加了一道与所有优化路径无关的兜底，保证不变式成立。
6. **指标混进无关因素** —— "重复率"先后混进 token 估算开销和面包屑，
   导致阈值怎么调都不对（降到 0 重叠仍有 43.85%）。
7. **参数化重构之后，调用点还在走不带参数的旧方法** —— 变体里的尺寸/重叠
   从未到达分块器，于是"尺寸扫描表 9 行数字完全相同"、对齐组号称 121 字实际跑 500 字。
   **两个实验同时变成废纸，而每个数字单看都合理。**
8. **差值对所有指标统一 ×100** —— `topKTokens` 印成 −44320.93（真实 −443.2）。
   率类指标要换成百分点，**量类指标（块数/token 数）不该乘**。
9. **对齐的扫描区间把 token 数当成字符数** —— `target × [0.6, 1.4]` 完全落不到目标附近
   （这批语料约 0.53 token/字符），二分一路走到边界，最后差 50 token（25%），
   而报告里照样写着"已对齐"。→ 改成用实测锚点外推 + 边界扩张。
10. **"0 表示默认值"的约定在调用点丢了** —— `topK=0` 被透传给检索器，
    而它的契约是"返回空列表"，于是等预算表整张全是 0。

> 这 10 条的共同点：**全都不报错，全都只在真实语料上才暴露**（第 7~10 条尤其典型）。
> 这也是为什么本模块的测试里有一批**结构性断言** ——
> "标题块数必须 > 20"、"9 个不同尺寸不能量出同一个数"、"两组平均块大小必须接近"、
> "预算表里必须装进来至少一条"、"RRF 分数必须等于名次倒数之和"、
> "说明文字不能残留未替换的占位符"。
> **"功能是否成功"的断言在这些退化面前会一路绿灯** —— 这一轮 4 个 bug 全是被上面那类断言抓出来的。
