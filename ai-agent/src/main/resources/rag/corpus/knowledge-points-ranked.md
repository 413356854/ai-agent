# AI Agent 应用岗 · 知识要点（按学习重要度排序）

> **调研时点：2026-09-11**｜数据源：101 份中文 JD 调研（2025-11）、JD 面试要求研究报告（2026-05-02，覆盖 BOSS/拉勾/51job/智联/猎聘/Greenhouse/Ashby/Levels.fyi）、347 份 Agent JD 能力分析（2026-08-21）、LangChain 生态岗位技能频次（2026-04）、Awesome-LLM-Interview 高频考点。

## 0. 先看三个反直觉的市场事实

**① 这不是 2025 年的市场了。** 岗位已从「概念词」变成边界清晰的工程岗，硬性要求高度趋同：**Python + LangChain/LangGraph + RAG + Tool Calling + 向量库 + Docker/K8s**。3–5 年经验普遍开 **25–60K·14/15 薪**，北京最高（均薪 40K+）。

**② 门槛已经变了 —— 最扎心的一条：**
> 「大部分人只做过 LangChain 调 API 的 demo，离真正的生产 Agent 还差一截。」（347 份 JD 调研，2026-08）

**③ Prompt 工程师独立岗位正在消失** —— 2025 年比 2023 年**减少约 70%**，正被「Agent 应用工程师」和「上下文工程」吸收。**这条路已经没有独立出口了**，必须走 Agent 工程线。

### 技能出现频次（LangChain 生态岗位，2026-04）

| 技能 | 频次 | 解读 |
|---|---|---|
| Python | **93.4%** | 通用默认，无争议 |
| AWS / Docker / GCP / K8s | 34.7% / 32.4% / 29.1% / 27.2% | **工程化是硬门槛，不是加分项** |
| LangChain | 34.3% | 但「只会它」= 中位 max $210K；会框架无关的 agent = $290K |
| LangGraph | 22.1% | 编排主流 |
| FastAPI | 17.4% | Python 后端底座 |
| TypeScript | 17.4% | 作为第二语言 |
| **MCP** | **16.9%** | **2026 年增速最快的单一技能** |
| LangSmith | 8.5% | 评估观测（低但关键，见 P0-3） |

## 1. 三档能力定位（先看清自己在哪一档）

来自 347 份 JD 的技能共现概率统计：

| 档位 | 内容 | 覆盖岗位 | 含义 |
|---|---|---|---|
| **基础档** | Python + LangChain/LlamaIndex + RAG + Prompt Engineering | ~70% | **够投简历，但会被同质化简历淹没** |
| **进阶档** | 大模型实战（有项目证明）+ 后端 API（FastAPI）+ Docker + MySQL/Redis | ~85% | **真正的竞争区** |
| **顶配档** | MCP / AutoGen / Dify（至少一个）+ 微调经验 + 高并发分布式设计 | ~95% | 看你想卷到什么程度 |

> **结论**：基础档不值钱（人人都有），**进阶档才是必争之地**，顶配档按需。
> 本文的 P0 = 基础档 + 进阶档 + 评估能力；P1 = 顶配档 + 生产纵深；P2/P3 = 按需与放弃。

# P0 · 决定性知识（不会直接淘汰）

## P0-1 编程与工程基本功 —— 权重最高，且最被低估

> Agent 工程师拆开看 **70% 是传统工程能力，30% 才是「Agent 专项」**。工程功底差一步，整套 agent 跑都跑不起来。

| # | 知识要点 | 重要度 | 学到什么程度 |
|---|---|---|---|
| 1 | **Python 精通**（含 async/await、类型标注、打包） | ★★★★★ | 93.4% 岗位要求；能写并发 + 限流 |
| 2 | **后端 API（FastAPI/Flask）** | ★★★★★ | Agent 服务化的底座，17.4% 明写 |
| 3 | **Docker** | ★★★★★ | 32.4%；容器化在中文 JD 出现 55 次 |
| 4 | **MySQL / Redis** | ★★★★☆ | 状态与缓存，进阶档必备 |
| 5 | 结构化输出三条路：JSON mode / tool schema / 约束解码 | ★★★★★ | 知道各场景取舍 |
| 6 | Pydantic 校验 + 自动修复重试（repair loop） | ★★★★★ | 修复循环必须设次数上限 |
| 7 | 流式（SSE / WebSocket）与增量渲染 | ★★★★☆ | 从 API 到前端全链路 |
| 8 | 超时 / 指数退避重试 / 限流 / 熔断 | ★★★★★ | 区分「可重试」与「重试无用」 |
| 9 | **token 计量与成本埋点**（每次调用都记） | ★★★★★ | 数据结构必须一开始就设计好 |
| 10 | 微服务 / 云平台 / CI/CD | ★★★☆☆ | 微服务 42 次、云平台 38 次、CI/CD 28 次 |
| 11 | 数据模型：会话 / 轮次 / 步骤 / 调用 四层 | ★★★★☆ | 决定后面 trace 好不好做 |
| 12 | K8s | ★★☆☆☆ | 27.2% 提及，但应用岗「会用」即可，别深调 |
| 13 | TypeScript | ★★☆☆☆ | 17.4%；作为第二语言，非必需 |
| 14 | C++ / CUDA | ★☆☆☆☆ | 45 次提及但来自芯片/嵌入式/推理岗，**应用岗忽略** |

> **反直觉提醒**：很多人以为 JS/TS 重要（因为 vibe coding），实际 JS/TS 只被提及 15 次，远低于 Python 的 125 次。**别在 TS 上花时间**。
> **同时**：这块是 P0-4 可观测性的前提 —— 没有调用级埋点，trace 和评测根本做不出来，所以埋点要早做。

## P0-2 上下文工程 —— 应用岗唯一的核心手艺

> 模型能力你改不了，能改的只有「喂进去什么」。
> **趋势信号**：目前只有极少数 JD 提到 Context Engineering，但 Anthropic 的 Applied AI Engineer JD 已明确要求 `prompting, context engineering, agent architectures`——**大概率在 2026 下半年成为 JD 标准词，现在学就是提前卡位**。

| # | 知识要点 | 重要度 | 学到什么程度 |
|---|---|---|---|
| 1 | system prompt 分层：身份 / 目标 / 红线 / 工具说明 / 输出格式 / 示例 | ★★★★★ | 能画出可复用模板 |
| 2 | **prompt 版本化**（git 管理 + A/B + 回归用例） | ★★★★★ | 「这三个字最值钱」，多数团队改一行上线就翻车 |
| 3 | 指令优先级：system > user > 工具返回 | ★★★★★ | 能说清被注入时靠什么兜住 |
| 4 | 上下文预算分配：系统/示例/历史/检索/工具结果 | ★★★★★ | 有具体数字，不是「大概」 |
| 5 | **上下文窗口管理**：lost-in-the-middle、摘要链 | ★★★★★ | 长对话不崩的核心 |
| 6 | 压缩三选一：滑动窗口 / 滚动摘要 / 关键事实抽取 | ★★★★★ | 知道各自丢什么 |
| 7 | 关键约束常驻（pin 每轮出现，绝不进摘要） | ★★★★☆ | 长对话不崩的关键技巧 |
| 8 | **上下文污染**：历史错误答案被反复复用 | ★★★★★ | 能说出「重开」触发条件 |
| 9 | 负面约束优于正面要求 | ★★★★☆ | 能把模糊要求改写为可判定禁止项 |
| 10 | few-shot：固定示例 vs 语义相似度动态选样 | ★★★★☆ | 知道不一致示例比没有更糟 |
| 11 | CoT / ToT：何时显式要求 | ★★★★☆ | 与 P2 的 Plan-and-Execute 呼应 |
| 12 | 输出 schema：枚举、必填、**拒答字段** | ★★★★★ | 必须留「信息不足」出口 |
| 13 | 约束过严 → 拒答率上升的权衡 | ★★★★☆ | 能报出「严格度 vs 成功率」曲线 |

> **验收话术**：「我不靠感觉调 prompt，每一版都有对应的评测数字。」——必须能报出 A → B。

## P0-3 工具调用 + Agent 循环 + MCP

> **这是 2026 年真正的分水岭：**
> 「一个只做 RAG + 调 LLM API 的人，叫 AI 工程师；一个在 MCP 之上设计工具调用、规划循环、记忆机制的人，才叫 Agent 工程师。」

### 3.1 工具设计

| # | 知识要点 | 重要度 |
|---|---|---|
| 1 | 工具 schema：名称、描述、参数、枚举、默认值、必填 | ★★★★★ |
| 2 | **描述即 prompt**：何时该用 / 何时不该用 / 失败返回什么 | ★★★★★ |
| 3 | 单位、格式、时区、取值范围写死在描述里 | ★★★★☆ |
| 4 | 枚举优于自由文本 | ★★★★☆ |
| 5 | 反模式：万能工具、语义重叠工具、返回超大 JSON | ★★★★☆ |
| 6 | **结构化错误回灌**（错误里带可用值，模型才能自愈） | ★★★★★ |
| 7 | 读工具 vs 写工具分类，写操作必须确认 | ★★★★★ |
| 8 | 幂等设计：重试不产生重复副作用 | ★★★★☆ |
| 9 | 工具数量膨胀 → 检索式 / 分组式工具选择 | ★★★☆☆ |

### 3.2 ReAct 循环（手写一遍）

| # | 知识要点 | 重要度 |
|---|---|---|
| 1 | think → act → observe 循环**手写实现** | ★★★★★ |
| 2 | 三重上限：最大步数 / 最大 token / 最大时长 | ★★★★★ |
| 3 | 重复动作检测（同工具同参数） | ★★★★★ |
| 4 | 终止条件三态：成功 / 失败 / 需人工 | ★★★★☆ |
| 5 | Observation 处理：截断、摘要、敏感信息过滤 | ★★★★☆ |
| 6 | ReAct 的固有缺点：串行延迟高、易死循环、上下文易溢出 | ★★★★☆ |

### 3.3 MCP（2026 增速第一技能，重点投入）

| # | 知识要点 | 重要度 |
|---|---|---|
| 1 | MCP 是什么：把工具/资源标准化暴露给模型的协议 | ★★★★★ |
| 2 | tools / resources / prompts 三者区别与选用 | ★★★★☆ |
| 3 | **把现有能力封装成 MCP Server** | ★★★★★ |
| 4 | stdio vs HTTP/SSE 传输的适用场景 | ★★★★☆ |
| 5 | 第三方 MCP Server 的权限与供应链风险 | ★★★★☆ |
| 6 | MCP vs Function Calling 的职责边界 | ★★★★☆ |
| 7 | （了解）A2A 协议：Agent 之间协作 | ★★☆☆☆ |

> **为什么 MCP 单列**：16.9% 频次、增速第一；Anthropic Applied AI Engineer 已把它列为 production 必备；「谁先把现有能力封成 MCP Server，谁就站在下半年的红利位」。
> **验收**：模型调错参数后能在 2 轮内自愈；三重上限齐全；手写过 1 个 MCP Server。

## P0-4 评测与可观测 —— 决定薪资档位 ★★

> **这是 2026 年最被低估的能力，也是最硬的终面门槛。**
> 原文警告：「Agent 行为天然不确定，传统单元测试写不干净；你必须会设计 eval 套件。**说不清评估策略的人，基本过不了技术终面。**」
> Anthropic 的 JD 也把 `evaluation frameworks`、`transcript analysis` 与 prompting、MCP 并列要求。

| # | 知识要点 | 重要度 | 学到什么程度 |
|---|---|---|---|
| 1 | 评测集从真实流量/需求采样，不自己编题 | ★★★★★ | 能说出采样来源 |
| 2 | 分层：简单 / 边界 / 对抗 / 已知难点 | ★★★★★ | 四层都要有样本 |
| 3 | 规模：起步 30–50，稳定后 100+ | ★★★★★ | 有确切条数 |
| 4 | LLM-as-judge 评分量规（rubric）写法 | ★★★★★ | 会写可判定的 rubric |
| 5 | judge 偏差：位置 / 长度 / 自我偏好 | ★★★★☆ | 能说三种缓解手段 |
| 6 | 双评委 + 人工抽检校准 | ★★★★☆ | judge 本身也要被评测 |
| 7 | **核心五指标**：任务成功率、工具调用正确率、平均步数、成本、P95 延迟 | ★★★★★ | 缺一不可 |
| 8 | 回归测试接入 CI，改一次 prompt 跑一遍 | ★★★★★ | 能演示「一键跑回归」 |
| 9 | **trace 埋点层级**：会话 / 轮次 / LLM 调用 / 工具调用 / 检索 | ★★★★★ | trace ≠ 日志，要可回放可聚合 |
| 10 | **transcript analysis**：读懂一次完整对话轨迹 | ★★★★☆ | Anthropic JD 明确要求 |
| 11 | 线上失败分类与告警 | ★★★★☆ | 按错误类型聚合 |
| 12 | 输入快照与可重放 | ★★★★★ | 复现线上问题的唯一手段 |
| 13 | 工具链：LangSmith / Langfuse / Braintrust | ★★★★☆ | **高频面试题**，会一个 |
| 14 | A/B、灰度、影子模式 | ★★★☆☆ | 上线策略 |
| 15 | golden set 防过拟合（定期换题） | ★★★★☆ | 评测集也会被「刷」 |
| 16 | 实验台账：假设 → 改动 → 指标 → 结论 | ★★★★☆ | 有可展示记录 |

> **最值钱的 30 秒**：「我建了 X 条评测集，把成功率从 62% 提到 88%，成本降了 Y%。」
> **注意**：LangSmith 只有 8.5% 频次，看起来不高 —— 但它是**过滤器**，不是**加分项**。频次低是因为写在 JD 里的少，而挂在终面上的多。

## P0-5 RAG（生产级，不是朴素版）

> **「朴素 RAG 不值钱，生产 RAG 才值钱。」** RAG + 向量库在 101 份 JD 中出现 **123 次 —— 几乎成为所有 AI Agent 项目的标准配置**。
> 要求已经细化：从「有相关经验即可」进化到**知识更新 + rerank + 多模态 RAG**。

| # | 知识要点 | 重要度 | 学到什么程度 |
|---|---|---|---|
| 1 | chunking：固定长度 / 语义切分 / 父子块 | ★★★★★ | 知道各自适用场景 |
| 2 | **混合检索**：向量 + BM25 + 元数据过滤 | ★★★★★ | 单一向量检索不够 |
| 3 | **rerank 与 top-k 调参** | ★★★★★ | 必须有数字，JD 已明写要求 |
| 4 | 向量库选型：Milvus / Chroma / pgvector / Pinecone / Weaviate / Qdrant | ★★★★☆ | Pinecone 18.8%、Weaviate 16.0% |
| 5 | **知识库持续更新机制** | ★★★★★ | JD 新增要求，别漏 |
| 6 | 查询改写：多查询扩展、HyDE、指代消解 | ★★★★☆ | 关注改写后的稳定性 |
| 7 | **检索质量评估**：Top-K 召回率、答案忠实度 | ★★★★★ | 「没评估能力的 RAG 项目 = 盲调」 |
| 8 | 引用溯源：每个结论点回原文 | ★★★★★ | 可验证性 |
| 9 | **「检索不到」时的正确行为：不编造** | ★★★★★ | 最容易翻车处 |
| 10 | embedding 选型与多语言表现 | ★★★☆☆ | 按需 |
| 11 | 多模态 RAG（文本/图像/视频/语音） | ★★★☆☆ | 新增趋势，加分 |
| 12 | 文档解析与清洗（PDF / 表格 / HTML） | ★★★★☆ | 脏活但决定上限 |

# P1 · 生产必备（决定「做过 Demo」还是「做过产品」）

## P1-1 可靠性与 HITL

> **65%+ 的 JD 明确写「落地」，没有证据的简历直接被过滤。**

| # | 知识要点 | 重要度 |
|---|---|---|
| 1 | **workflow vs agent 判断标准**（步骤可枚举 → workflow） | ★★★★★ |
| 2 | 断点恢复：进程被杀后从检查点续跑 | ★★★★★ |
| 3 | 状态持久化（checkpointer）与状态 schema 设计 | ★★★★★ |
| 4 | 重试 / 降级 / 熔断（fallback 模型或固定流程） | ★★★★★ |
| 5 | HITL：审批节点、审批超时、异步人工介入 | ★★★★★ |
| 6 | 危险操作分级：只读 / 可撤销 / 不可撤销 | ★★★★☆ |
| 7 | 长任务：后台队列、进度反馈、取消 | ★★★★☆ |
| 8 | 混合模式：外层固定流程 + 内层局部 agent | ★★★★☆ |

> **架构判断题几乎必考**：「为什么这里用 Agent 而不是固定流程？」
> 标准答案：**能枚举步骤就别用 agent，agent 只会引入不确定性。**

## P1-2 安全与权限边界

> 安全行业是当前**第一大 Agent 应用领域**，这块被问到的概率比想象中高。
> 高频系统设计题：**Tool Registry → Router → Policy Engine → Approval Service → Executor Sandbox → Audit/Trace**，重点讲权限边界、高危动作确认、幂等、注入防护。

| # | 知识要点 | 重要度 |
|---|---|---|
| 1 | **工具/文档返回一律视为不可信数据，不能当指令执行** | ★★★★★ |
| 2 | prompt injection：直接注入 / 间接注入（检索文档）/ 工具返回投毒 | ★★★★★ |
| 3 | **能力白名单**（只能调 N 个工具、只能写某张表） | ★★★★★ |
| 4 | 输入隔离、指令层级、输出校验 | ★★★★★ |
| 5 | 代码/命令执行沙箱化（Executor Sandbox） | ★★★★☆ |
| 6 | 权限边界 + 高危动作确认 + 审计日志 | ★★★★☆ |
| 7 | PII 识别与跨租户数据隔离 | ★★★★☆ |
| 8 | 滥用防护：速率限制、成本上限、异常行为检测 | ★★★★☆ |
| 9 | 红队自测（20 条攻击用例） | ★★★☆☆ |

## P1-3 Memory 与多智能体（分水岭，但别过度投入）

**Memory / 状态管理** —— Agent 专项的核心组成之一：

| # | 知识要点 | 重要度 |
|---|---|---|
| 1 | 记忆分类：工作 / 情景 / 语义 / 程序性 | ★★★☆☆ |
| 2 | **写入策略**：何时写、去重、冲突消解、置信度 | ★★★★★ |
| 3 | 遗忘与更新：过期、被否定、用户要求遗忘 | ★★★★☆ |
| 4 | 记忆污染：错误记忆长期污染回答 | ★★★★★ |
| 5 | 三级记忆机制与上下文溢出的关系 | ★★★★☆ |
| 6 | 记忆与 RAG 的边界（私有事实 vs 公共知识） | ★★★★☆ |

**多智能体 / Multi-Agent**：

- **趋势**：JD 已从「单一 AI Agent」转向「多 Agent / Multi-Agent」，实际是**门槛在变高**（涉及 agent 间协作、上下文管理）。
- **但 OpenAI 自己给工程团队的忠告是**：「先用好一个 Agent 的全部能力，再考虑拆多 Agent。」每多一个 agent 就多一份协调开销、token 成本与失败面。
- **正确姿势**：只在**独立验证、异构工具、清晰领域边界**三种情况下上多智能体；能讲清 Reflection、Supervisor 等协作模式即可，**不要为「多」而「多」**。

## P1-4 行业垂域知识 —— 正在变成硬通货

> 「2026 年越来越多 Agent 岗位 JD 写『优先有 X 行业经验』——行业知识正在变成 Agent 工程师的硬通货。」

当前需求最明确的三个垂直方向：
1. **医疗健康**：体检报告/病历解读、健康信息管理
2. **金融服务**：智能投顾、风控（银行 + 传统车企是传统企业里的主力招聘方）
3. **教育培训**：个性化学习、智能答疑

其余高频：法律（Harvey）、电商搜索、智能客服/外呼、IoT/智能家居、安全。
**另外 9.1% 的岗位来自科研院所和高校** —— 学术机构在 Agent 领域比其他技术岗活跃得多。

## P2-1 框架与 SDK（会用即可）

**2026 年主流格局**：
- **国内 JD 高频**：LangChain / LangGraph（大多数要求「熟练」或「精通」）、Coze、Dify、AutoGen、CrewAI、Spring AI Alibaba
- **海外 JD 高频**：Anthropic SDK / OpenAI Agents SDK / **Claude Agent SDK**（上升期）、MCP、Claude Code

> **被忽视的机会**：101 份 JD 中**没有任何一个提到 Claude Code SDK**，但它「具备了开发一个 Agent 所需要的几乎全部功能」。
> **薪资差异信号**：framework-agnostic 的 agent 岗位中位 max **$290K**，只会 LangChain 的中位 **$210K**。
> **正确姿势**：先手写循环（P0-3），再用框架重写一遍，**对比框架替你做了哪些决策**。这话术的含金量远高于「我会用 LangGraph」。

**LangGraph 只需理解 6 个概念**：State/reducer、Node/Edge/条件边、Checkpointer、interrupt、子图、流式事件粒度。

## P2-2 ReAct vs Plan-and-Execute（高频考点）

| 维度 | ReAct | Plan-and-Execute |
|---|---|---|
| 规划时机 | 边走边想（在线） | 先规划后执行（离线） |
| 灵活性 | 高（适应环境变化） | 低（计划可能过时） |
| 全局最优 | 弱（贪心每步） | 强（考虑全局） |
| LLM 调用数 | 多（每步都调） | 少 |
| 可审查性 | 差（需追踪全链） | **好（计划可单独审查修改）** |
| 适用 | 探索性、不确定环境 | 目标明确的复杂任务 |

> 面试常问「ReAct 和 Plan-and-Execute 怎么选」——答案取决于**任务是否可预规划 + 是否需要人审计划**。

## P2-3 微调的判断力（不学流程）

只需一句话：**「什么时候该微调，什么时候该改 prompt / 加检索？」**
> 格式与风格 → prompt/few-shot；知识时效 → RAG；**只有当「能力/分布」本身不足且有几千条高质量标注数据时才微调**。
> 注意：微调在**月薪 60K+ 的高端岗位**中几乎必备（SFT/LoRA/QLoRA，出现 42 次），但应用岗不必现在投入。

# 3. 学习顺序结论（直接照做）

```
第 1 步  P0-1 的最小可用子集：Python async + FastAPI + 结构化输出 + Pydantic 修复 + 成本埋点
        └─ 不要系统学完工程，只学能跑通最小闭环的部分
第 2 步  P0-2 上下文工程（边学边改主线项目，开始做 prompt 版本化）
第 3 步  P0-3 工具调用 + 手写 ReAct 循环 + 1 个 MCP Server
        └─ 此时应有一个「能跑、但不可靠」的 Agent
第 4 步  P0-4 评测与可观测  ← 分水岭，从这里开始你才算「做过产品」
第 5 步  P0-5 生产级 RAG（含知识更新 + rerank + 检索评估）
第 6 步  P1-1 可靠性/HITL + P1-2 安全（有了评测才知道该修哪里）
第 7 步  P1-3 Memory / 多智能体 + P1-4 行业垂域（按目标岗位选择）
第 8 步  P2 框架重写（用评测分数对比手写版）
```

### 四条铁律

1. **P0-4 评测必须早于 P2 框架**。先有尺子再谈优化，否则所有「改好了」都没有证据。
2. **不要停在基础档**。基础档（Python + LangChain + RAG + Prompt）覆盖 70% 岗位，但也覆盖了绝大多数简历 —— **进阶档（实战项目 + FastAPI + Docker + DB）才是竞争区**。
3. **一切都落到同一个代码库**，不要为知识点开新 Demo。
4. **每个 P0 块学完必须产出一个数字**（成功率 / 成本 / 延迟 / 步数），否则等于没学。

### 简历公式（重要）

> **技术栈 + 规模 + 效果指标 + 上线状态**
>
> 示例：「使用 LangChain 构建 5 种 Tool Calling 链，支持天气/搜索/数据库，Top-5 召回率 89%，已上线服务 200 日活」
> 对比：「会用 LangChain」—— **后者直接掉一档**。

# 5. 高频失败模式速查

| 症状 | 常见根因 | 对症 |
|---|---|---|
| 模型不调工具，光聊天 | 工具描述太抽象 | 重写描述，明确「何时必须调用」 |
| 反复调同一个工具 | 缺重复检测 / 错误回灌信息不足 | 去重 + 错误里带可用值 |
| 长对话后变傻 | 上下文污染 / 压缩丢约束 | 关键约束常驻 + 摘要 + 定期重开 |
| 输出格式随机崩 | schema 太复杂 / 无修复循环 | 简化 schema + 校验后自动修复 |
| 检索到了但答错 | 噪声块干扰 / 没要求引用 | rerank + 强制引用 + 无据拒答 |
| 演示好看上线就废 | 无评测、无边界用例 | golden set + 对抗样本 + CI |
| 成本失控 | 无路由、无缓存、步数无上限 | 小模型路由 + 缓存 + 步数上限 |
| 被注入攻击 | 把工具/文档返回当指令 | 输入分级 + 能力白名单 + 输出校验 |
| **说不清评估策略** | **只做过 demo** | **建 eval 套件 —— 这条直接卡终面** |

# 附录 · 术语速查

- **MCP**：Model Context Protocol，把工具与资源标准化暴露给模型的协议，**2026 年增速最快的单一技能**。
- **A2A**：Agent-to-Agent 协议，解决 agent 之间的协作（了解即可）。
- **ReAct**：Reason + Act，模型交替思考与调用工具的基础范式。
- **Plan-and-Execute**：先出计划再逐步执行，可审查性优于 ReAct。
- **HITL**：Human-in-the-loop，关键节点插入人工审批。
- **LLM-as-judge**：用模型按评分量规打分，需与人工校准。
- **golden set**：固定的人工确认过的评测样本集，用于回归测试。
- **transcript analysis**：分析一次完整对话轨迹来定位质量问题（Anthropic JD 明确要求）。
- **FDE**：Forward Deployed Engineer，嵌入客户现场做交付的工程岗（海外高薪路径）。
- **lost-in-the-middle**：长上下文中部信息易被忽略的现象。
- **上下文污染**：历史中的错误内容被反复复用，导致持续答错。
- **能力白名单**：限制 agent 只能调用被显式允许的工具/资源，最可靠的防线。
