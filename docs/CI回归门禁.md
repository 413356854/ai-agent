## 一、它为什么存在：把四道门禁变成一条命令

在这个脚本之前，这个仓库已经有四道各自独立的验证，而它们**散落在四条命令、四个工作目录、
两个必须先起起来的服务、一组环境变量**里：

| 门禁 | 原来怎么跑 | 谁在跑 |
|---|---|---|
| 后端测试（328 个） | `cd ai-agent && mvn -o test` | 顺手会跑（IDE 里就有） |
| **离线评测回归基线** | 之前**没有**这道门禁（只有一份打印报告） | —— |
| 界面自检（假后端 283 项） | `pnpm mock` + `pnpm dev:mock` + `UI_URL=… pnpm check:ui` | 基本靠记得 |
| 界面自检（真后端 182 项） | 还要先起后端、再起另一个端口的 vite、再带 `CHECK_EXPECT_REFLECTION=0` | 更难记得 |

那种状态下的真实后果**不是"麻烦"，而是门禁会被跳过**：
一个人改了分块参数，他会跑后端测试（顺手），
而"评测基线有没有动"需要一条他记不住的命令 —— 于是那道门禁**事实上不存在**。

所以这一步的产出是一件很小但很关键的东西：**一条命令**。

## 二、怎么跑

```bash
node scripts/ci.mjs                            # 后端测试（含离线评测回归基线）
node scripts/ci.mjs --with-ui                  # 再加界面自检（假后端，跑两遍）
node scripts/ci.mjs --with-ui --with-real-ui   # 再加真后端路径（需要 8080 上已跑着后端）
```

退出码：`0` 全过；`1` 有门禁失败（**fail-fast**，失败之后不再跑后面的）。

产物（都可直接看，不必翻终端滚屏）：

| 文件 | 是什么 |
|---|---|
| `ai-agent/target/rag-regression-report.txt` | 离线评测回归门禁的**人读报告**（UTF-8） |
| `ai-agent/target/rag-actual.json` | 本次实测的全部指标 |
| `ci-logs/<门禁名>.log` | 各道门禁的完整输出（每道一个文件） |
| `web/ui-check-out/` | 界面自检的截图 |

### 两个环境变量（只在需要时设）

| 变量 | 默认 | 什么时候要改 |
|---|---|---|
| `CHECK_BROWSER_CHANNEL` | `chrome` | **在 CI 上必须设成 `chromium`**（干净容器里没有 Chrome，见下） |
| `CI_REAL_BACKEND` | `http://127.0.0.1:8080` | 真后端不在本机默认端口时 |

## 三、为什么界面的那两道门禁**默认不跑**，而且"没跑"会被打印出来

它们需要 Playwright + 一个浏览器内核，而干净 CI 容器里通常都没有。
一道**默认会红、且红的原因与代码无关**的门禁，几次之后就会被加进忽略列表 ——
那时它保护的东西就悄悄没了。

所以它们是显式的 `--with-ui` / `--with-real-ui`，并且脚本末尾会专门打一段：

```
[ci] ⚠️ 本次**未执行**的门禁（"全绿"不代表它们过了）：
  - 界面自检（假后端）—— 加 --with-ui 打开（需要 Playwright + 本机 Chrome）
```

**这一段不是装饰。** 不说的话，"这次全绿"会被读成"四道门禁都过了"，
而真相是其中两道压根没跑 —— 一个被跳过的门禁比没有门禁更危险，
因为它提供的是**虚假的安心**。

## 四、离线评测回归基线：这一件新增的那道门禁

### 4.1 它补的是哪一个洞

在它之前，43 条评测集的结果只被**打印**出来（`RagEvidenceReportTest`）。
那个类的取舍本身是对的（把具体数值钉成断言会让"调参"变成"改测试"），
但它留了一个真实的洞：**打印出来的数字没有人会逐行比对**。
于是"召回率悄悄掉了 3 个百分点"可以存在很久，直到某天有人翻报告才发现 ——
而那时已经不知道是哪一次改动造成的。

### 4.2 为什么它敢用"逐位比较"

因为这条链路**完全确定**：固定语料（仓库里的 4 份文档）+ 固定评测集（43 条）+ 本地 BM25。
无模型、无网络、无时间依赖。**实测连跑两次，4 位小数逐位相同。**

确定性的东西用阈值是有害的：一个"允许掉 5%"的阈值会放过 4.9% 的退化，
而放过一次就会放过第二次 —— 累积到最后没人知道退化从哪次开始。
所以判据是「**和基线不一样就要被看见**」，容差 `1e-9` 只用来吸收浮点噪声。

### 4.3 红了怎么办（两种情形，处置正好相反）

| 情形 | 怎么认出来 | 怎么做 |
|---|---|---|
| **真退化** | 你这轮没动语料/分块/检索，而数字掉了 | 去查代码。**这正是它存在的理由** |
| **有意的变更** | 你刚调了分块参数 / 改了语料 / 加了用例 / 修正了过期标注 | 重采基线，并在 `note` 里写清为什么动 |

⚠️ **这两种在数字上长得一模一样**，判断只能靠人。
这也正是这条基线**刻意不做自动更新**的原因 —— 一个会自己更新的基线等于没有基线。

重新采基线（只在情形 ② 做）：

```bash
cd ai-agent
mvn -o test -Dtest=RagRegressionTest -DfailIfNoSpecifiedTests=false -Drag.baseline.write=true
# 然后把 target/rag-baseline-candidate.json 里的 note 改写清楚，合并进
#   ai-agent/src/test/resources/rag-baseline.json
```

### 4.4 基线里存了什么，以及为什么元信息必须一起存

`ai-agent/src/test/resources/rag-baseline.json`（**随代码进版本控制**）：

```json
{
  "schema": "rag-baseline/v1",
  "takenAt": "2026-09-17",
  "note": "…为什么采这一版…",
  "strategies": ["fixed-size", "structural"],
  "evalSet": "classpath:rag/eval-set.tsv",
  "caseCount": 43,
  "documents": 4,
  "metrics": { "fixed-size": { "recallAt5": 0.814, … }, "structural": { … } }
}
```

三样东西各自防一种错：

- **`schema`**：格式一变就换值，读到不认识的值时**拒绝比较**（不是勉强读）。
  勉强读旧格式的后果很隐蔽：缺的字段会是 `0.0`，
  于是"基线说 recall@5 = 0"会表现成一堆看起来像"严重退化"的红；
- **`note` 必填**：没有"为什么采这一版"的基线，半年后没人敢动它，也没人敢信它；
- **`strategies` / `evalSet` / `caseCount` / `documents`**：比较之前先核对**采集条件**。
  换了语料或改了用例数时，数字变了是**当然的**，
  而"当然的变化"不该被报成退化 —— 那会消耗对这条断言的信任，最后被人注释掉。

### 4.5 方向判据：为什么"召回变大"不该报红

指标分两类，而**这个区分本身就是判据**：

- **越大越好**：`recall@1/3/5/10`、`mrr`、`precision@5`；
- **越小越好**：`chunkCount`、`avgChunkTokens`、`maxChunkTokens`、`totalTokens`、
  `duplicationRatio`、`undersizedChunks`。

把两类混在一起写"变了就红"，会在**召回变好**时也报红 ——
而那种误报会让人开始习惯性忽略这条断言。

> `avgChunkTokens` / `maxChunkTokens` 归到"越小越好"是**刻意的**：
> 块越大，相关性判定里的"块覆盖了答案章节"就越容易成立（已知的混杂因素，
> 见 `RagEvaluationService` 的类注释）。所以"块变大"本身就该被看见，
> 而不是被当成中性事件。

方向判据有**单独的、不需要跑评测的**测试（`directionJudgementIsCorrect` /
`unregisteredMetricDirectionThrows`）：端到端那条红了的时候，
人需要立刻知道"是数字真的变了，还是判据错了"—— 这两者的处置完全相反。

## 五、★ 这道门禁**不**回答什么（这一节比上面的代码重要）

路线文档给这一件的名字是「改一次 Prompt 跑一遍回归」，
而它最容易导致的一个误解是：**以为跑完它就知道"新提示词更好"了**。

**它不知道。** 原因很具体，必须写清楚：

> 离线评测链路是 **解析 → 分块 → BM25 → 指标**，这条路上**一次模型调用都没有**。
> `RagEvaluationService` 里没有任何地方读提示词。
> 所以**提示词的文本对这里的任何一个数字都没有影响** ——
> 你把系统提示词整段删掉，这 43 条用例的 Recall@5 一个数都不会变。

那么"改了 Prompt 跑一遍回归"到底得到了什么？诚实的两条：

| 它**能**回答 | 它**不能**回答 |
|---|---|
| 「这次改动没有把**其余部分**带坏」（检索链路、持久化、HITL、MCP、界面全都没被碰坏） | 「新提示词比旧提示词**更好**」 |
| 「提示词的**结构**没被改坏」（围栏配平、关键段落还在、篇幅没有异常） | 「答案质量有没有下降」 |
| 「提示词**真的被发出去了**」（`PromptHotReloadTest` 抓出站请求体逐字节比对） | 「某类问题上的表现如何」（需要按 tag 分组看真模型的表现） |

**后一列需要什么**：一个真 key + 一批问题 + 一套评判口径（人工标注或模型裁判）。
本项目目前**没有**——本机没有可用的 key（`/ask` 一律 401），
所以这一列是**明确的缺口**，而不是"已经做了但没写文档"。
它与台账里已经单列的两条是同一族：

- 「**自愈率没有真实数字**」—— 三个自愈场景用的是脚本化模型 + 假端点，
  证明的是"回填内容正确且真的进了下一轮请求"，不是模型的真实表现；
- 「**整窗缓存命中率 0% 有两种成因**」—— 数据本身分不出来，只有真 key 能区分。

### 所以，"改 Prompt 的正确流程"是什么

1. 在界面第七种模式里**存**新版（**存与生效是两次决定**，先存不生效）；
2. 看校验判据：**拒绝级**会拦住坏内容，**警告级**（篇幅骤变）要人判断；
3. 跑 `node scripts/ci.mjs`（或至少 `mvn -o test`）——
   它证明**其余部分没被带坏**，且提示词结构、指纹传递仍然成立；
4. 决定是否**生效**（界面上有二次确认，并写明影响范围）；
5. 生效之后**盯一会儿**：答案质量下降**不会报错**——
   接口 200、模型照样回答、字数甚至差不多。这是这一层最重要的性质，
   也是为什么第 3 步只能证明"没带坏"，证明不了"变好了"。
6. 变差了就**回滚**（回滚也是新增一版，历史里留着这次回滚）。

## 六、CI 平台怎么接

### 6.1 任何平台（推荐先这样）

只要三步，与平台无关：

```bash
node scripts/ci.mjs                 # 核心门禁，退出码即结论
```

- **不需要** Playwright、不需要浏览器、不需要网络（Maven 用 `-o`）；
- 环境要求：**JDK 21 + Maven + Node**（与开发本机一致）；
- 产物按上面第二节的清单收集即可。

### 6.2 GitHub Actions

`.github/workflows/regression.yml` 已经写好。它做两件事：
① 核心门禁（必跑）；② 界面门禁（装了浏览器才跑，并设 `CHECK_BROWSER_CHANNEL=chromium`）。

> ⚠️ **这个 workflow 在本机没有被真正执行过** —— 本仓库当前**没有配置 git remote**
> （`git remote -v` 为空），所以它从未在 GitHub 的 runner 上跑过一次。
> 能保证的是：它调用的每一条命令都在本机真跑过（`node scripts/ci.mjs --with-ui` 全绿），
> YAML 语法也是有效的。**不能保证**的是 GitHub 环境特有的那些事
> （runner 上的 JDK/Maven 版本、Playwright 依赖安装、缓存行为）。
> 第一次推上去之后请按下面的"首次接入要盯什么"核对一遍。

#### 首次接入要盯什么

1. **`mvn` 能不能离线跑**：workflow 里用了 `-o`。如果 runner 的本地仓库是空的，
   离线解析会直接失败 —— 那时要么去掉 `-o`（首次联网预热），
   要么加一步 `mvn -B dependency:go-offline`；
2. **Playwright 安装**：`npx playwright install --with-deps chromium` 之后
   **必须**设 `CHECK_BROWSER_CHANNEL=chromium`。不设的话它会去找系统 Chrome，
   而 runner 上没有 —— 失败信息是 `Executable doesn't exist`，看起来像"界面坏了"；
3. **端口**：界面门禁会占 8081 / 5173（真路径再占 5174）。
   runner 上一般干净，但若与别的 job 并行过，用 `CI_MOCK_PORT` / `CI_UI_PORT` 换一组；
4. **`strictPort` 的陷阱**：`vite.config.ts` 里是 `strictPort: true`。
   端口被占时 Vite **起不来**，而在旧实现里 `UI_URL` 仍然打得到那个旧进程 ——
   于是你以为在验新代码，其实验的是旧服务（第九轮踩过）。
   `scripts/ci.mjs` 已经处理了这件事：它先 `waitForHttp` 等**自己起的**那个端口，
   起不来就直接失败；真后端路径还会核对 `awaitingRecovery` 这个"我打到了谁"的指纹。

## 七、这一件之后，"改坏了能回滚"才真正闭环

路线文档阶段四的三句验收口径，现在是这个状态：

| 口径 | 靠什么 |
|---|---|
| Agent 出问题**有人能查** | 五层 trace（`/api/agent/runs/{id}/trace`） |
| 成本异常**有人能发现** | 成本看板（**还差"有人被通知"**——告警在剩的第 5 件里） |
| Prompt 改坏**能回滚** | 版本管理（只追加历史 + 回滚也是新增一版） |

而**"改了之后怎么知道没改坏"** 这一问，在这一件之前只能靠人看。
现在它有了三条自动化的答案（见第 5 节那张表的第一列）——
以及一条**明确标注出来的边界**（第二列）。

**一个没有被验证的结论，写清楚它没被验证，比给它一个好看的绿灯更有用。**
