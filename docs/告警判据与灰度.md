## 1. 这一件补的是哪半句话

路线文档对阶段四的验收写的是三句：

| 验收口径 | 在这一件之前的状态 |
|---|---|
| Agent 出问题**有人能查** | ✅ 第十三轮的五层 trace |
| 成本异常**有人能发现** | ⚠️ **只做到一半**：成本看板能*看见*异常（`notes` 里那几条 ⚠️），但"看见"的前提是**有人恰好打开那一页** |
| Prompt 改坏**能回滚** | ✅ 第十二轮的版本管理 |

第二句缺的那一半是它最安静的失败方式：**没有人被通知**。
所以这一件做两件事：

1. **告警**：把那些"人读的 ⚠️"变成**可查询、可确认、会自己出现和消失的事件**；
2. **灰度**：把"新版到底比旧版好还是差"从"不可回答"变成"**有数据可答**"——
   Prompt 版本管理答得了"改哪一版、能不能回滚、当时用的是哪一版"，
   但它答不了"哪一版更好"，那需要**分组流量**。

## 2. 四条纪律（每一条都对应一种"不报错的错"）

### 2.1 判据只有一份，而且分两个阶段

`AlertRule` 是「什么算异常」的唯一一份定义，**阈值、严重度、处置说明三样都在里面**。

它按**两个时间点**分成两半，而分类标准不是"有多严重"，是
「**这个判断在构建阶段能不能得出结论**」：

| 阶段 | 谁评估 | 典型判据 | 为什么在这一侧 |
|---|---|---|---|
| `GATE`（构建阶段） | `RagRegressionTest`、`scripts/ci.mjs` | 离线评测基线漂移、采集条件不一致、指标方向未登记、门禁脚本被 git 忽略 | 它们需要的输入（固定语料、固定评测集、本地 BM25）**在构建机上都齐**，结论完全确定 |
| `OBSERVE`（运行阶段） | `AlertEvaluator` | 价格没配 / 模型没价 / 对不上账 / **某租户**缓存命中为 0 / 租户花费集中 / 连续空命中 / 灰度没流量 … | "价格没配"在干净的 CI 环境里**永远是未配**——把它做成门禁，就是一条"默认会红且与代码无关"的门禁 |

> ⚠️ 这个分类是本件最容易做错的一处。直觉会说"严重的挡门禁、不严重的只告警"，
> 而那是错的：一条**默认就会红、且红的原因与代码无关**的门禁比没有门禁更糟，
> 因为它教会人忽略红色（台账里那条纪律）。

#### ★ 主体粒度：逐条判据的一个显式决定（阶段四第 6 件补的一条纪律）

租户维度出现之后，"这条判据说的是**谁**"从"只有一个答案"变成了一个必须**逐条回答**的问题。
答案写在 `AlertEvaluator.judge` 里那处显式的 `switch`，而它的判据不是"粒度越细越好"：

| 粒度 | 判据 | 为什么 |
|---|---|---|
| **全局** | 价格没配、对不上账、连续空命中、灰度两条 | 它们问的是「**取数/配置本身对不对**」——那个答案与有几个租户无关。按租户拆开问只会得到 N 条一模一样的话，而"同一件事说 N 遍"就是让人开始不看告警的最快方式 |
| **每租户** | **某租户缓存命中率为 0**、**租户花费集中** | 它们问的是「**花钱的形态有没有异常**」——只有在租户粒度上才有可处置的动作（去看那一家的提示词前缀 / 去确认那是不是一个大客户） |
| **每模型** | 模型没价 | 单价是按**模型**配的，与谁在用无关。按租户拆开会得到"甲租户的模型 X 没价"这种**无法处置**的告警（补一次价就够） |

> ★ **为什么它不是判据上的一个属性（枚举字段），也不是一个部署配置**
> 属性会带来"声明与实现不一致"（声明 per-tenant、lambda 里却只读窗口合计 —— 没有症状，
> 只是永远少报几条）；配置更糟：同一份判据目录会**读不同的意思**，
> 于是"这条判据在说什么"取决于部署设置，而判据的意义不该是配置。
> 所以它是写死在代码里、能被对着快照断言的一件事 —— `AlertRuleCatalogTest` 里
> `costRulesDeclareTheirSubjectGranularity` 就是钉它的那条测试：
> **改了粒度，那条测试会告诉你哪些判据的粒度变了。**

> ⚠️ **"未标注租户"永远不是一个主体。** 它是一堆互不相干的运行的合计，
> 把那个合计当成"一个租户"去报警会得到一条没有处置动作的告警
> （"未标注租户 的缓存命中率为 0" —— 要补的是调用方的 `tenantId`，不是"优化未标注租户"）。
> 所以逐租户的判据**只在真的标注了租户的运行上展开**；一个还没接归因的部署会退回窗口口径，
> 于是"整个部署都没命中缓存"这件事仍然会被看见。

**改判据的成本是刻意的**：阈值不放进 `application.properties`。
一个**能被调低**的阈值，会在"告警响了但没人管"的时候被顺手调低 ——
而那一刻它就不再是判据了，它变成了"让页面变绿"的开关。

### 2.2 通知只在**状态变化**时发生

| 情形 | 行为 | 为什么 |
|---|---|---|
| 没响 → 响 | 通报一次 | 这是新问题 |
| 一直响着 | **不通报**，只更新 `occurrences` 与 `lastSeenAt` | 一天评估 288 次就是 288 条一样的话 —— 后果不是"他看烦了"，是**他开始不看** |
| 响 → 不响 | 通报一次（恢复） | 恢复也要能对上此前那条 |
| **压根没评估**（取数失败 / 构建阶段的判据） | **什么都不做** | ⚠️ 见下 |

> ★ **取数失败绝不能把"正在响的告警"标成已恢复**。一次数据库抖动就把所有告警刷成
> "已恢复"的话，**故障看起来自己好了** —— 而那是所有观测系统里最坏的假象，
> 它会把正在排查的人直接劝退。所以 `AlertEvaluator.Outcome` 里
> `SKIPPED`（没评估）与 `QUIET`（评估了、没响）是两种形态，只有后者能触发恢复。

### 2.3 恢复是「改状态」，不是「删行」

`alert_event` 里**没有 delete**（`AlertStore` 接口上就没这个方法）。
一条告警恢复之后留在表里，带 `resolved_at`：

- 删掉的话，"它到底响过没有"在复盘时无从回答（**复盘的第一句话**就是它）；
- `first_seen_at` **永远不被改写**（持续响着只更新 `last_seen_at`）——
  顺手更新它会让"这个问题存在了多久"永远接近 0；
- 修好又坏了 → `resolved_at` 清空、状态回 `OPEN`，重新出现在"未处理"里。留在
  `RESOLVED` 里的话，"修好过又坏了"会被静默地当成"一直没修好"。

这与 Prompt 版本管理那条"回滚也是新增一版"、成本看板那条"调价新增一条"是同一条纪律：
**会改写历史的操作，事后无法解释。**

### 2.4 三态，不是一个布尔

`OPEN`（没人看过）/ `ACKNOWLEDGED`（看过、暂时不管）/ `RESOLVED`（已恢复）。

合成一个布尔的后果很具体：值班的人确认完一轮之后，列表看起来与"完全没人管"
一模一样 —— 于是下一个人会从头再查一遍，而**第三个人就开始忽略这个列表**。
分开之后，"还有几条没人看过"（`openCount`）是一个能直接读出来的数字。

⚠️ 而**已确认的不会被下一次评估抹掉**：`state` 只在"上一状态是 `RESOLVED`"
或本来就 `OPEN` 时才回到 `OPEN`。写成直接 `state='OPEN'` 的话，系统每评估一遍
就把人的确认抹掉一次，而值班的人只会觉得"这个按钮时灵时不灵"
（**这一条上线前的测试抓出来的**，见台账第 15 轮踩坑 #93）。

## 3. 怎么用

### 3.1 端点

| 端点 | 回答什么 | 谁用 |
|---|---|---|
| `GET /api/alerts/rules` | "这个项目把什么算作异常"（含构建阶段的门禁） | 人 + 接监控的说明书，**一次库都不查** |
| `GET /api/alerts` | "现在有什么在响、响多久了、有人看过吗" | 页面 / 值班 |
| `GET /api/alerts/sweep?days=7` | 跑一轮评估并返回结果（`dryRun=true` 则只算不写） | 页面刷新 / cron / 监控探针 |
| `POST /api/alerts/{fingerprint}/ack` | "我看过了" | 值班的人 |
| `GET /api/canary?kind=system-agent-tools` | "有没有在放量、配置多少、**实际分到多少**" | 页面 |
| `POST /api/canary/start` | 开一次实验 | 人 |
| `POST /api/canary/stop` | 停一次实验（`endReason` 必填） | 人 |

### 3.2 接到真正的通知通道上去

现在**只有日志**：`AlertRecorder.notify(event, firing)` 打 WARN（响）与 INFO（恢复）。
这是刻意的取舍 —— webhook / 邮件需要凭据、重试策略、以及"发了但没收到怎么办"，
那些是运维接入的事。而**通知点集中在一个方法里**，接 webhook 时只改那一处。

⚠️ 但必须说清一个代价：**没有人调 `sweep`，就永远没有告警记录**。
界面刻意不替你决定（进面板自动跑会让"打开这一页看看"这个动作本身改变状态）。
真上生产要挂一个定时器 —— `GET /api/alerts/sweep` 是个普通 GET，cron 直接打就行。

### 3.3 灰度怎么用（一个完整的往返）

```bash
# 1) 先在 Prompt 面板（或 POST /api/prompts/system-agent-tools/versions）存一版新的
#    ⚠️ 保存**不会**让它生效 —— 灰度成立的前提就是"候选版还没生效"
# 2) 开 20% 的灰度，并写清这次想验证什么（必填）
curl -X POST http://127.0.0.1:8080/api/canary/start -H 'Content-Type: application/json' -d '{
  "kind":"system-agent-tools", "candidateVersion":2, "weightPercent":20,
  "note":"验证新版对工具选择的影响", "by":"zhangsan"}'
# 3) 跑几个任务，然后看**实际分到了多少**（不是"配置写了几成"）
curl http://127.0.0.1:8080/api/canary | jq '.split'
# 4) 停掉，并写清为什么停（推全 / 回滚 / 只是到期了）
curl -X POST http://127.0.0.1:8080/api/canary/stop -H 'Content-Type: application/json' \
  -d '{"endReason":"新版观察正常，准备推全","by":"zhangsan"}'
```

四个前置条件（不满足一律 400，并把判据说清）：

1. 候选版本必须**已存在**；
2. 候选版本**不能就是当前生效那一版** —— 那样两组跑的是同一份提示词，实验什么都证明不了；
3. 重量必须在 **1..99**（0 等于没开却看起来开着；100 是发布，不是灰度）；
4. 必须写**实验假设**（不写的话一周后没人记得，唯一结局就是忘了关）。

## 4. 灰度的分流：算出来的，不是存下来的

`decide()` 拿**运行 id** 取 SHA-256、取模 100，再与重量比。三个决定各自都能被反驳：

| 决定 | 理由 |
|---|---|
| 哈希用 SHA-256，**不用 `String.hashCode()`** | 后者在不同 JVM 实现之间不保证一致，而"分桶不稳定"的表现是"新版那一组的数字莫名其妙地不稳定" |
| 分桶输入是**运行 id**，不是会话 id、更不是随机数 | 用会话 id 会让同一段对话的所有运行落同一组（样本量看着够，有效样本是"对话数"）；随机数更糟 —— 同一个运行 id 两次判定会得到两个结果 |
| 取模 **100**，不用 0..1 的浮点 | 整数分桶没有边界抖动，而且桶值能直接印在界面上（`bucket=17/20%` 比 `hash=0.17` 好核对） |

于是**不需要**一张"运行 → 分组"的映射表，也就不存在"映射表与配置不一致"这个状态。
存映射表还有个更坏的后果：它让"这次走的是新版"变成一个**可以被改写**的字段，
而分组一旦能被改写，"两组对比"就失去了全部意义。

**代价说清**：分流函数改了（比如换成另一种哈希），已经跑过的那批属于哪一组
**不会跟着变**（那是历史），但新运行的分布会变。所以**真实分组同时落进了 trace**：

- `agent_step.canary_variant` = `canary` / `stable` / 空串；
- ⚠️ **空串与 `stable` 是两件事**：前者是"这次实验不包含它"（灰度还没开），
  后者是"它是这次实验的对照组"。混起来会让灰度报告的**参与率虚高** ——
  而参与率虚高的直接后果是"样本够了"这个判断过早成立。

## 5. 灰度特有的两类失败（各有一条判据盯着）

| 失败 | 长什么样 | 判据 |
|---|---|---|
| **配置写着 20%，实际一份都没分到** | 所有功能正常、日志干干净净、配置也还在 —— 唯一的问题是**实验等于没做**，而使用者以为做过了，并据此得出"新版没有区别" | `canary-no-traffic` |
| **配置 20%、实测 5%**（样本足够时） | 分流函数有问题（哈希偏斜、或者压根没接上而只是碰巧几份走了新版） | `canary-split-biased` |

★ 而第二条判据里**最小样本量**（10 份）与阈值同等重要：
10% 的重量在 5 份样本里"一份都没分到"的概率高达 59%，允许小样本判定的话，
这条告警会在每次刚开灰度时**必然误报一次** —— 而误报三次之后，人就再也不看它了。
所以**样本不足时界面不许显示"偏了多少"**，只显示"还差几份"。

## 6. 它**不**回答什么（与数字一起交付）

- ❌ **灰度答不了"新版更好"** —— 它答的是"**分流有没有按比例发生**"。
  "哪一版更好"要一批问题 + 一套评判口径，本项目还没有
  （与"自愈率没有真实数字"同族）。
- ❌ **构建阶段的门禁在这一页不评估** —— 它们的结论要去 CI 上看（`AlertRule` 里登记了 3 条，
  2026-09-18 删掉了第 4 条 `GATE_ENTRY_NOT_COMMITTABLE`：它守的那条 `.gitignore` 规则被取消后，
  这条判据没有可执行的判定，而**一条永远不会响的门禁与没有这条门禁在任何观测上一样**）。
  页面上把这几条单独列出来并标成"这一页不评估"，就是为了防止读的人
  以为"告警面板说构建也没问题"。
- ❌ **缓存命中率为 0 有两种成因**（真没命中 / 上游不返回缓存字段），
  数据本身分不出来 —— 判据只说"有两种可能"并给出唯一能分辨的动作（拿真 key 看原始 usage）。
- ❌ **trace 里的 `retrieval_hit.token_count` 是估算**，而成本看板的 token 来自上游
  `usage`（事实）。两个口径同时出现在界面上，混用会把估算当记账。
- ⚠️ **写操作默认未受保护**：`ai.alert.write-token` 是空的，任何能访问这个端口的人
  都能确认告警。响应里会明确标注 `writeProtected=false`，让"忘了配"变成界面上
  一行看得见的字。
- ⚠️ **`/api/alerts/sweep` 是个会写库的 GET**。这是个刻意违反 HTTP 语义的取舍：
  它要被 curl / 浏览器 / 监控探针直接打，不需要构造请求体。
  补偿是 `dryRun=true` —— 那是这一组端点里唯一的纯读入口。

## 7. 这一件里的可执行证据（不是叙述）

| 证据 | 怎么看 |
|---|---|
| 判据本身的边界 | `AlertRuleCatalogTest`（17 项，不需要起容器）：每条判据的"刚好响 / 刚好不响"两侧 + 抄写的阈值与公开常量一致 |
| 通知时机 | `AlertRecorderTest`（7 项）：只在状态变化时通报、取数失败绝不标恢复、构建阶段的判据不被运行阶段标恢复 |
| 落库语义 | `AlertStoreTest`（12 项）：UPSERT 四条语义（occurrences 累加 / first_seen_at 不动 / resolved 清空 / 已确认保持）、确认的前置条件、排序稳定 |
| 灰度判定 | `CanaryRulesTest`（14 项）：分桶确定性、跨 JVM 稳定、分布均匀、四个前置条件、降级路径 |
| ★ **端到端** | `CanaryRoutingTest`（3 项）：**抓出站请求体**证明"命中候选版的那次运行，发出去的确实是候选版正文"—— 而不是"decide() 返回了候选版" |
| 界面 | `web/verify-ui.mjs` 第 8 节（两条路径都跑） |
