# AI Agent 控制台（前端）

对接 Spring Boot 后端的**类后台管理界面**：左侧一条目录，右侧上下两块（页头 + 内容）。
目录分两区 ——

| 区 | 里面是什么 |
|---|---|
| **AI Agent 对话台** | 八个模式：SSE 流式对话 / 结构化输出 / 线程与预算（诊断取证）/ RAG 分块评测（离线链路）/ Agent 工具调用（含**人工确认 HITL**）/ 成本看板 / Prompt 版本 / 告警与灰度 |
| **AI Agent 应用管理** | 三项：**用户管理**（**已接线**：账号 / 口令 / 启用状态，见「第九区」）、**权限管理**（**已接线**：角色 / 角色能调哪些工具 / 能在哪些目录下干活 / 角色成员，见「第十区」）与 **agent任务**（**已接线**：派活 / 确认 / 执行 / 验收的卡片看板，见「第十一区」） |

技术栈：**React 19 + Vite 8 + TypeScript + Ant Design 6**。

## 外壳：左侧目录 / 页头 / 内容

```text
┌──────────────┬────────────────────────────────────────────┐
│ AI Agent 控制台│ AI Agent 对话台        [分区标签]  conversationId… 新会话 │
│ ▾对话台       ├────────────────────────────────────────────┤
│  SSE 流式     │                                            │
│  结构化输出    │            当前视图（只有这一块滚动）           │
│  …八个模式     │                                            │
│ ▾应用管理      │                                            │
│  用户管理      │                                            │
│  权限管理      │                                            │
│  agent任务     │                                            │
│ ☰ 收起目录     │                                            │
└──────────────┴────────────────────────────────────────────┘
```

三条约束（改布局时不要动，自检里都钉着）：

| 约束 | 为什么 | 谁来守 |
|---|---|---|
| **只有内容区滚动** | 目录与页头要一直在视口里 —— 往下翻成本看板时还得看得见"这一页是哪个区" | `height: 100%` 一路传下去；每一层 flex 都写 `min-height: 0` |
| **页面不许横向溢出** | 诊断页里的表格本来就宽，外壳再溢出一条就分不清是谁溢出的 | 自检在 `documentElement` 上断言 `scrollWidth - clientWidth === 0`；窄屏只能由目录自己变窄 |
| **当前项不靠颜色单独表达** | 目录收起后文字全藏起来，"现在在哪一项"只剩左边那条 3px 色标与 `aria-current` | 自检断言"收起后仍读得出当前项" |

**目录为什么可以收起**：它占 232px，而这一页的主体是数据表（成本看板、五层 trace、版本历史），
1100px 宽的窗口下那 232px 是"差一行、差一列能不能放下"的差别。
收起态存 `localStorage`（刷新一次就忘掉会很烦），但**窄屏（≤900px）不写回** ——
那是"窗口放不下"的临时妥协，写回去会让一个窄窗口永久改掉这台机器上的偏好。

**为什么一级目录名也可点（折叠一段）**：整条目录的收起是**横向**省宽度，
分组折叠是**纵向**省高度 —— 对话台那段有八项，在应用管理里干活时它们只是占位。
折叠态同样存 `localStorage`（`ai-agent.nav.group-collapsed`，按分组键记），
但**窄条态（railed）下忽略**：那时标题那一行整行是藏起来的、点都点不到，
再按折叠态渲染就会让某一段一项都不显示，看起来像那一段坏了。
⚠️ 折叠**只改渲染**，不改"当前在哪"：收起的那一段里若正落着当前视图，
标题会带上着色与左侧 3px 色标（自检断言 `data-active-inside=1`）——
"现在在哪"与"目录收起后仍读得出当前项"是同一个要求的两处。

**切模式一律走目录项**：`verify-ui.mjs` 里收成了一个 `navMode(label)` 函数。
散着写 16 个选择器的话，改一次布局就要改 16 处，而漏改的那一处**不会报错** ——
它会点中另一个同名元素或超时，症状看起来像"那个面板坏了"。
它点之前要先把目录与**被折叠的分组**都展平：折叠态会跨节保留，
而收起来的那一段里项根本不在 DOM 里 —— 症状与"目录收起了"完全一样。

> **这一层只有两个文件管导航**：`src/nav.ts` 定义 `Mode`、两段目录、每段的标题与标签；
> `src/components/AppSidebar.tsx` 画目录。加一个视图要改两处 —— `NAV_SECTIONS` 和
> `App.tsx` 里那串渲染分支（旧版是三处：联合类型、`Segmented` 的 options、头部那排 Tag 文案）。

## 跑起来

```bash
# 1) 起后端（另开一个终端，需要 JDK 21）
cd ../ai-agent && run.cmd

# 2) 起前端
pnpm install
pnpm dev            # http://127.0.0.1:5173
```

不想配 API Key / 不想烧 token 时，用假后端验证渲染（**八个模式的端点都支持**）：

```bash
pnpm mock           # 终端 A：假后端 → http://127.0.0.1:8081
pnpm dev:mock       # 终端 B：前端代理指向假后端
```

假后端的结构化端点会故意造一个"**回灌过一轮**"的结果（第 1 轮 `confidence` 写成百分制被校验拦下），
因为那才是这个功能真正值得看的样子；提问里带「降级」二字则返回 `degraded` 结果，用来看降级态。
假后端的 Agent 端点带一个**审批状态机**（详见「第六种」一节之外的那段说明），
所以点「批准 / 拒绝」会真的改变后续 `/ask` 的返回 —— 那是"人在闸门上的介入"在界面上可演练的前提。

## 界面自检（浏览器真跑一遍）

> **推荐先试一条命令**（第十四轮起；2026-09-18 后端测试整体删除之后，它的默认动作也跟着变了）：
> 从仓库根目录跑
> ```bash
> node scripts/ci.mjs                  # 默认：界面自检（自己起假后端与 vite，连跑两遍验确定性）
> node scripts/ci.mjs --with-real-ui   # 再加真后端路径（需 8080 先起后端）
> node scripts/ci.mjs --with-ui        # 与默认同义 —— 老写法仍然认，不必改习惯
> ```
> 它会自己管服务生命周期（起、等就绪、任何退出路径都清理）。
> 下面那几条手工命令仍然有效，适合只想单独跑界面自检的时候。
> ⚠️ 它现在**只有界面自检这一道门禁**：后端那边已经没有任何自动化测试了，
> 所以"全绿"只代表界面这一层过了，**不代表后端逻辑被验过**。
> 自检本身的行为与边界（哪些分支只在假后端上跑、哪些断言故意放宽）写在 `web/verify-ui.mjs`
> 的文件头注释与本节里。

```bash
pnpm mock           # 终端 A（或先起真后端）
pnpm dev            # 终端 B
pnpm check:ui       # 终端 C：打 http://127.0.0.1:5173
```

打**真后端**时（模型一次就答对、也不会因为提问里带「降级」二字而真降级）：

```bash
CHECK_EXPECT_REFLECTION=0 UI_URL=http://127.0.0.1:5199 pnpm check:ui
```

`CHECK_EXPECT_REFLECTION=0` 的含义是"别断言回灌/降级/完整轨迹/审批这两条分支"——
假后端里那些结果是写死的，断言才有确定性；真实模型没有"必然回灌""必然降级"的输入，
硬断言必然误报。⚠️ 降级路径原先由后端单测覆盖（那个测试类已随后端测试整体删除），
**现在没有自动化守着它，界面自检也不断言它** —— 要验只能在后端上手工打一遍（见 `ai-agent/README.md` 的「已知未验证项」）。

### 用哪个浏览器内核（`CHECK_BROWSER_CHANNEL`）

默认 `chrome`（用系统已装的 Chrome，理由是实测过的一个环境问题：本机 Playwright 自带的
chromium 内核版本对不上，直接 launch 会报 `Executable doesn't exist`）。

⚠️ **在 CI 上必须设成 `chromium`**，并先装内核：

```bash
npx playwright install --with-deps chromium
CHECK_BROWSER_CHANNEL=chromium node scripts/ci.mjs
```
（`node scripts/ci.mjs` 默认跑的就是界面自检；`--with-ui` 与不写它完全同义。）

不设的话它会去找系统 Chrome，而干净的 runner 上没有 ——
失败信息是 `Executable doesn't exist`，**看起来像"界面坏了"，其实是环境问题**。
（这个开关是第十四轮加的：在那之前频道是写死的 `chrome`，
而那意味着这道门禁**在 CI 上永远红** —— 一道"红的原因与代码无关"的门禁，
几次之后就会被加进忽略列表，那时它保护的东西就悄悄没了。）

### 两条路径为什么条数不同、以及各验的是什么

**实测（2026-09-21，加进 agent任务那一节之后）**：

| 路径 | 实际执行 |
|---|---|
| 假后端（默认） | **442 项，全过**，控制台干净（`node scripts/ci.mjs` 连跑两遍，两遍都是 442 / 全过，2026-09-22）。这个数**由脚本自己在收尾时报出**（`✅ 全部通过（N 项断言）`，`N` 是 `expect()` 被调用的次数）—— 手工数要同时判断每个分支走没走到，那种账迟早对不上 |
| 真后端（`--with-real-ui`，`CHECK_EXPECT_REFLECTION=0`） | 最近一次留下日志的是 **230 项执行 / 8 项红**（`ci-logs/02-ui-check-real.log`）。⚠️ 用户管理 / 权限管理那两节（`[8.6]` / `[8.7]`）新增于那之后，**真后端路径没有整条重跑过**；权限那部分的只读断言单独对真后端跑过 9/9（见 5.8） |

真后端那些红**没有一个来自界面改动**，判据是它们给的原因全都是"没有数据"：
本机用的是假 key，上游一律 401，于是**一次运行都没被记下来**，
而 `/api/agent/runs` 为空会把成本 / 价格 / 告警那三节的断言连着带红
（那三节的假数据里刻意塞了行，真后端上什么都没有）：

| 红的是哪一节 | 实测到的东西 |
|---|---|
| 流式 / 结构化 | 上游 401（既有的：假 key 没有内容可渲染） |
| Agent 历史 / 失败细分 | `GET /api/agent/runs` 是**空的**（401 ⇒ 没有运行被落库） |
| 成本看板（4 条） | 价格表为空 ⇒ 页面显示的是"算不出"那条路径，而断言在找"刻意不给 0"的说明 |
| 告警与灰度（3 条） | `一条告警记录都没有` —— 没有运行 ⇒ 判据一条都不响 |

⚠️ **真后端这一行不是"一个数字"，而是一个范围**：它读的是**库里的数据** ——
同一天三次单跑分别是 230/14、175/20 与 238/8，差别在于"那一刻库里有多少运行、有多少条告警"，
以及"有几节因为前置数据为空而提前走了另一条分支"。所以这一行的用法是
**判断"红的是不是同一族（数据为空）"**，而不是拿它跟某个数字比大小。
（判定"这一轮的红是不是新引入的"有一条硬判据：**列出来的那几条必须全在"没有数据"那一族里**。
8 项红逐条看过，名字与上表同类 —— 而"库是 MySQL"那条断言在这一轮里是绿的。）

⚠️ **别把这一行读成"真后端路径是绿的"**：它证明的是"契约对得上、页面能渲染"，
而"这些面板有数据时长什么样"只在假后端上验过（假数据的形状与真后端逐字段一致，数值不是）。
**一个会随环境变化的数字，两个取值都要写下来** ——
否则读的人没法判断某次输出是不是正常。（核实方式：看这次运行最后那行 `✅ 全部通过（N 项断言）` ——
`N` 由脚本自己数，不要凭印象写。这条规矩来自阶段一的一次虚报：本项目曾写成"36 项"而单条路径实际只执行 29 项。）

### ⚠️ 第十二轮改掉的三条"写死了环境假设"的断言（值得单独记）

这三条都**不是**功能缺陷，而是断言本身把"当前环境恰好会怎么分类/有几版"当成了事实。
它们的共同症状是：**在功能完全正常时变红，而失败信息看起来像界面坏了。**

| 原来的写法 | 为什么错 | 改成 |
|---|---|---|
| `/UPSTREAM_AUTH/.test(runsText)`（真后端） | 假设"假 key → 401 → 必然分到 `UPSTREAM_AUTH`"。实测这一轮分到的是 **`UNEXPECTED`**（上游 401 经 SDK 包装后没被认成鉴权失败） | 断言"失败细分那一格有值，且是六个合法分类之一"——**分类准不准不是界面自检的职责**（原先由 `AgentFailureClassifier` 的后端单测钉，那批测试已在 2026-09-18 整体删除，现在**没有自动化守着它**） |
| `/重试没有意义\|API Key\|鉴权/`（处置建议） | 同样是假设了某一种失败的措辞。`UNEXPECTED` 给的是一句**完全正确**的建议：「没能归类的异常……请直接看日志堆栈」 | 断言"建议非空且含可操作动作词"（建议/重试/检查/看日志…） |
| `hasText: /^生效$/`、`hasText: '对比'` | **antd 会给两个汉字的按钮文案插一个空格**（"生效" → "生 效"、"对比" → "对 比"），精确匹配永远找不到；而失败信息只说"找不到按钮" | 用 `/^生\s*效$/` 这类容错正则（与「antd 给恰好两个汉字的按钮插了字间距空格」同族，例如「关闭」被渲染成「关 闭」） |

> 一条通用经验：**断言的判据要落在"这一页负责的东西"上。**
> 界面自检负责"渲染出来了、能读、能点"；至于"上游 401 该被分成哪一类"、
> "这一版内容与那一版是否相同"，那是后端该钉的事。
> ⚠️ 而后端那批测试已在 2026-09-18 整体删除 —— 这两件事**现在没有任何自动化守着**，
> 别指望在别处看到红灯。
> 越界去断言别人的职责，换来的就是"环境一变就红、而红得毫无信息量"。

> 本轮还改掉了**假后端状态机**带来的一类问题：Prompt 面板的假后端是**有状态**的
> （存/生效/回滚会真的改内存里的版本表），所以自检第一步必须 `POST /api/prompts/__reset`，
> 否则跑第二遍时会继承第一遍改出来的版本号，"存一版之后版本数 +1"这类断言必红，
> 而红的原因与功能无关。这与 HITL 靠 `__reset-approval` 做到确定性是同一条经验。
> **实测：同一份脚本连跑两遍，两遍都是 253 项全过。**

### ⚠️ "真后端路径"可能在骗你（第九轮踩到，务必先查一个数字）

`vite.config.ts` 里写了 `strictPort: true`。所以如果**之前那个 `pnpm dev:mock` 还占着 5173**，
新起的 `pnpm dev`（指向真后端）会**启动失败**，而 `UI_URL` 仍然打得到 5173 ——
于是你以为在跑"真后端路径"，实际打的是假后端。症状是：断言数对不上、
报告里出现一堆"只有假后端才有"的结论、而失败原因看起来像界面出了问题。

**区分方法（一个数字就够）**：

```bash
curl http://127.0.0.1:5173/api/agent/runs     # 看 awaitingRecovery
#   假后端固定给 1，真后端是 0
```

RAG 面板（第四种模式）与 HITL 的界面部分**不需要真模型**：前者是离线链路（调模型 0 次），
后者只依赖审批端点（纯读库 + 写一行状态）。所以打真后端跑自检时，
唯一会失败的是流式/结构化那两条需要真 key 的路径，
以及**依赖"库里有数据"的那几节**（历史运行 / 成本 / 告警）——
假 key 下 401 一律不落库，那三节就没有东西可渲染（实测清单见上面那张表）。

**对齐实验那 18 项里有 2 项不打开浏览器**：它们直接 `import` 假数据文件，
断言"三组已对齐的对照里右侧更差""不对齐块大小那组能看出块更大的效应"。
这么写是因为**这份面板上的解读文字与数字是绑定的**，而自检断言不了"文字和数字是否一致" ——
只能把"结论方向"本身变成断言，否则有人顺手改了 mock 数字，
界面会变成"文字说结论反了、数字说没反"，而所有基于文案的断言照样全绿。

为什么要有这个脚本，而不是"我自己点一遍就算验证"：点一遍只证明"我这次看到的对"，
证明不了"下次改动后还是对的"；而且有几个问题**肉眼看不出来** —— 横向溢出、
Ant Design 的 deprecation 警告、控制台报错。当前模型看不了截图，所以脚本刻意用
**几何断言**代替"肉眼看布局"（`documentElement.scrollWidth - clientWidth > 0` 就说明有横向溢出）。

> **第九轮新增的一条自检纪律**：断言里有**异步状态转移**时（例如"点批准 → 轮询把那条待批捡走"），
> 一律用 `waitFor(...)` 轮询条件，**不要用固定 `waitForTimeout`**。
> 固定 sleep 只有两种结局：睡太短会闪断（CI/慢机器上必红），睡太长拖慢整条自检 ——
> 而**闪断的断言最后总会被注释掉**，那时它保护的东西就悄悄没了。
> 本轮因此改了 4 处等待（其中一处是真的红过一次：`切回 Agent 后任务结果仍在`）。

> **同一族里最新的一条（左侧目录那一轮踩到）**：新写的布局断言一开始把
> "点一下收起开关"读成"点了没反应"、"目录没占宽度"，而**功能完全正常**。
> 根因是**断言抢在 React 提交之前读**：`click()` 返回时状态更新未必已渲进 DOM，
> 而目录宽度还要过一遍 CSS 过渡（0.2s）。
> 改法与上面那条同一套 —— 不读"我以为已经发生的事"，而是 `waitFor` 那个结果本身
> （状态属性、几何宽度）。**"读早了"与"读错了"在报告里长得一模一样**，
> 这是固定 sleep 之外的第二类假红。

> ⚠️ **怀疑自检本身有问题时，先确认你打的那个端口上是谁**（2026-09-20 踩到）：
> 假后端端口上留着上一轮的进程时，它不报错，只是"旧代码 + 旧状态"，
> 于是断言红在很怪的地方 —— 实测症状是"流式回答只渲染出 8 个字符""结构化没有回灌"
> "钉住实验 90 秒等不到结果"。判据：假后端的 `GET /api/agent/runs` → `awaitingRecovery` 恒为 1
> （真后端与旧进程都是 0），更彻底的是先确认端口没人监听。

## 两种模式的差别（这就是要对照的东西）

| | SSE 流式 | 结构化输出 |
|---|---|---|
| 端点 | `POST /api/chat/stream` | `POST /api/chat/structured` |
| 传输 | `text/event-stream`，逐字推 | 普通 JSON，一次返回 |
| 回答 | 自由文本 | 固定结构 `{answer, confidence, keywords}` |
| 正确性保障 | 无（模型说什么就是什么） | **JSR-380 校验 + 回灌重答 + 兜底** |
| 失败语义 | 吐多少算多少，失败发 `error` 事件 | **全有或全无**，失败给降级结果 |
| 停止按钮 | 有（可以只要半截） | **没有**（取消拿不到半成品，还白烧已跑的 token） |
| temperature | 用户可调 | 固定 0.0（后端钉死，故界面不给滑块） |
| 超时 | 首字节 30s / 空闲 30s / 整体 180s | 一刀切 60s（可能要跑多轮回灌） |

**为什么把两种模式做成同一个界面里的切换**：它们的差别本身就是这个项目要讲的东西 ——
同样一次模型调用，一个逐字推自由文本，一个同步等结构化结果。放一起才能直接对比
"同样的提问，两种契约下拿到的东西有什么不同"。
两个 hook 都挂在 `App` 上（不是按模式条件挂载），所以来回切模式**不会丢掉已有记录**。

## 第三种模式：线程与预算（运行时取证）

这一页不放"回答"，放的是**只有改造真的生效才成立的运行时事实**。它对应后端的两个学习点：

| 部件 | 端点 | 它证的是什么 |
|---|---|---|
| 当前线程 | `GET /api/diag/threads` | `virtual` 是**容器层是否换上虚拟线程**的唯一直接证据（来自 `Thread.isVirtual()`，不是读配置）。配置写错了 Boot 会静默忽略，所以这里把"配置意图"和"运行时事实"并排显示 |
| 线程账目 | `GET /api/diag/threads/stats`、`POST .../stats/reset` | 平台线程数（`ThreadMXBean`，**不含虚拟线程**）与业务口径的并发峰值。重置按钮是为连续做对照实验准备的：peak 是单调递增的，上一组会把这一组顶住 |
| 载体复用 | `GET /api/diag/threads/carriers` | 16 个虚拟线程只落到少数几个 `ForkJoinPool-1-worker-*` 上 —— "并发数 ≫ 线程数"长什么样 |
| **钉住对照** | `GET /api/diag/threads/pin` | 本页最值钱的一块：两组实验除阻塞方式外完全相同，`synchronized` 会把载体线程钉住导致探针延迟冲到秒级，`ReentrantLock` 则是毫秒级 |
| 预算切分 | `GET /api/diag/threads/config` | `窗口 × (1-安全边际) = 可用预算`，再切出一块给输出，剩下的才是输入上限；三段按真实 token 数按比例画成一条色带 |
| 非流式对话 | `GET /api/chat/async`（+ `/sync` 对照） | 预算校验在这条链路上真的跑过；同时把非流式端点的回答和耗时摆出来 |

两个实测坑（都体现在代码里）：

- **`carriers` 的 `virtualThread` 字段实测是空字符串**：`Executors.newVirtualThreadPerTaskExecutor()`
  不给线程起名。所以它既不能当 React key（16 条样本会撞成同一个 key，控制台直接吐重复 key 警告），
  也不一定有内容可显示——面板上虚拟线程那一栏只计数，复用的证据靠"每个载体背了几个任务"表达。
- **`pin` 的字段名是 `probeLatencyWith*`，不是 `queueLatencyWith*`**：这个实验返工过一次，
  第一版"先启动占位任务、睡一会儿再量延迟"两组都量到 0ms（`runAsync` 在提交时就选好了载体，
  而"载体刚好被占满"是个很窄的时间窗口）。现在改成"分批投放 + 每批连测多次探针取最大值"，
  指标名也跟着换了。对照组的 0ms 是正常结果，不是数据缺失。

面板和两个对话 hook 一样挂在 `App` 上，所以来回切模式**实验数据不会丢**（钉住实验一次要跑两秒以上，
重跑代价太大）。它自己有一条 defer 规则：**第一次切到这个模式才发请求** ——
虚拟线程计数要遍历所有线程抓栈，用户一直待在流式模式时不该白打。

## 第四种模式：RAG 分块评测（离线链路，调模型 0 次）

这一页是四种模式里最特殊的：**它完全不调用模型**。量的是"文档怎么切、检索找不找得到"，
对应阶段二（RAG）。排查顺序就是卡片的排列顺序 —— 解析不对，后面全是白费功夫。

| 部件 | 端点 | 它证的是什么 |
|---|---|---|
| 语料解析 | `GET /api/diag/rag/corpus` | 4 份文档读成了多少个块、**块类型分布**。其中「标题块」是关键：为 0 说明标题层级没被识别，那么"按标题层级分块"从未发生，而**整条链路不报任何错**（实测踩过：Tika 把 Markdown 当纯文本，13KB 带 19 个标题的文档被解析成 1 个段落）。所以那一项单独做显眼判定 |
| 分块预览 | `GET /api/diag/rag/preview` | 直接看块长什么样。**面包屑**是最值得看的字段：结构分块有、固定硬切恒为空 —— 那正是两者最本质的差别。切策略会自动重跑，方便对照 |
| 分词诊断 | `GET /api/diag/rag/tokens` | 提问被切成了什么。中文走二元组（`虚拟线程` → `虚拟/拟线/线程`），**这是检索失败的第一现场**：块切得对不对肉眼能看出来，token 看不出来 |
| 召回 | `GET /api/diag/rag/retrieve` | 单条提问捞回了哪些块，带名次、分数、**归属章节**。排查"召回错了"时看的是归属章节，不是分数 |
| **策略对照** | `GET /api/diag/rag/compare` | 两种分块策略并排：Recall@k / MRR / ContextPrecision + **token 成本**，再给差值（百分点） |
| **块大小对齐实验** | `GET /api/diag/rag/align` | 本页的**主角**：把对照组的块大小二分收敛到与实验组同大小之后重跑 —— 消掉混杂因素后**结论反了**（见下） |
| 评测集 | `GET /api/diag/rag/eval-set` | 43 条标注用例与分组。**"别只问两三个问题觉得还行"** —— 样本不够时页面上会明确警告"不能作为结论引用" |

### 对齐实验（`/align`）—— 为什么它不是"又一张对照表"

`/compare` 的结论**不可归因**：两组平均块大小不同（232.5 vs 200.6 token），
而判定标准是「检索到的块有没有覆盖答案所在章节」—— **块越大越容易覆盖答案**。
于是那 4.66 个百分点的差距里，多少来自"切点选在哪"、多少来自"块更大"，分不开。

`/align` 把这件事按住之后重跑，报告里给的是（2026-09-18 重测，真后端 2.8 秒 / 184585 字节）：

| 组 | 配置 | 块数 | 平均 token | Recall@5 | MRR | 全语料 token | 重复率 |
|---|---|---|---|---|---|---|---|
| `fixed-aligned-202` | 434 字/43 重叠（**收敛出来的对照组**） | 181 | 202.8 | **0.8372** | **0.6469** | **36707** | **13.74%** |
| `structural-nobc` | max-tokens 400，**关面包屑** | 193 | 202.4 | 0.7442 | 0.5244 | 39061 | 21.03% |

平均块差 **0.41 token** → 在这个前提下固定硬切**全面占优**，且**三路检索下方向一致**
（ΔMRR：词法 −12.25pp、向量 −9.80pp、混合 −8.21pp）。结构分块整体省 token
是"**它的块更小**"的副作用，不是策略的收益。

界面（`components/AlignmentPanel.tsx`）刻意做的几件事：

1. **7 组对照按检索方式分三堆**，不是平铺 —— 3+3+1 平铺会看不出"哪几组是一对"。
2. **每一行两行成对**（左＝参照方 / 右＝被考察方），差值一律"右 − 左"（后端定死的方向，
   前端不再猜）。只显示一侧就等于没做对照，而"只显示一侧"正是这类报告最典型的失败形态。
3. **"能不能判断切点"的标签打在每一行上，不打在分组表头上**。
   第一版打在分组表头上，结果 vector / hybrid 两个分组被整体标成"对齐的是渲染后大小"——
   而它们的第一组恰恰是最干净的那一组。根因：一个分组里混着两种性质的对照。
   自检里有一条断言钉住两种标签的数量（3 个 / 4 个）。
4. **差值列只放后端真给了差值的指标**。第一版加过一个「Δ全语料 token」列，
   而 `deltasBetween` 根本没算这个键 —— 整列 7 行全是「-」，
   看起来像"差值为零"或"数据缺失"，真相是**这个指标不存在**。
   表里永远为空的一列比没有这一列更糟：它把"我没实现"伪装成"结果就是没差别"。
5. **收敛过程整张表露出来**（9 个扫描点 + 收敛点高亮），并且**最优点落在区间端点时当场告警**。
   这条实验的第一版就是栽在这里：扫描区间写成 `target × [0.6, 1.4]`（把 token 数当成了字符数），
   整个区间都在目标以下，最后选了个差 50 token（25%）的点，而报告里照样写着"已对齐"。
6. **"向量那一路是离线哈希近似品"必须显示**：界面上摆着 `vector-local` 的 Recall@5 = 0.35，
   不解释它是什么，任何人都会拿它去和 BM25 的 0.74 比，得出"向量检索差一半"这个**完全错误**的结论
   （差的是"近似品 vs 真检索"，不是检索方式）。
7. **等预算表旁边写明"只有词法那一路有数"**：后端只为词法算 `budgetAlignment`，
   另外两路为空是**设计如此**。不写清楚，读者会把"设计如此"看成"界面漏渲染"，
   或者更糟 —— 以为预算结论适用于三种检索方式。

### 这一页刻意做的一件事：把"不能证明什么"写在界面上

实测结论是「换分块策略**没有**提升召回率，省的是 token」。但真正会被误读的不是这个结论，
而是那张对照表本身：0.7674 和 0.8140 摆在一起，任何人都会自行脑补出一个方向性结论。
所以界面上直接写明了三点 —— 其中第三点是关键：

> **不能说"语义分块更好"或"更差"**：相关性判定用的是「检索到的块有没有覆盖答案所在章节」，
> 而**块越大越容易碰到答案**。对照组平均块更大（232.5 token vs 200.6），
> 所以那个 Recall 差异里混着块大小的差异。要下结论必须先做"块大小对齐"的实验。

> ⚠️ 第三点的后半句后来改掉了：**那个实验已经做完了**（见上面「对齐实验」一节），
> 所以文案改成指向下面那份报告。**留着旧文案比没有文案更糟** ——
> 它会让人以为结论还悬着，进而自己脑补一个方向（多半偏向"结构分块更好"）。

配套的一个细节：差值块的颜色**按每个指标自己的方向**上色，而不是统一"涨了就是绿"。
`前 3 条 token` 涨了是坏事，`Recall` 涨了是好事 —— 统一配色会稳定地把读者引向错误结论。
自检脚本里有断言钉住这一点（必须同时出现 `is-good` 与 `is-bad` 两种颜色）。

### 假后端也实现了这 7 个端点

`mock/rag-routes.mjs`（对齐实验的数据在 `mock/rag-align-data.mjs`，由
`scripts/gen-align-mock.mjs` 从**真后端的一次实测响应**生成，瘦身只删不造）。
判据是：真后端这些数字每次都不一样（语料重新分块、检索分数变化），
拿它做自检只能写出很松的断言。所以假数据的数值取自**真后端的一次实测**，
形状（嵌套结构、字符串数字键）与真后端逐字段一致 ——
**数字是假的，形状是真的**；用真实数值还顺带保证了假数据与界面上的解读文字同向，
不会出现"文字说没有提升、数字却显示提升"的自相矛盾。

用法：`pnpm mock`（8081）+ `VITE_API_TARGET=http://127.0.0.1:8081 pnpm dev`。

### 这一页的实测验证

- 假后端：**全过**，控制台零错误零警告（整条脚本实测 **165 项**，含 RAG 与 Agent/HITL 全部）
- 真后端：RAG 相关断言**全部通过**（7 个端点的键集合与假后端逐一比对，**完全一致**；
  对齐实验 18 项全过）
- 两侧都验证过，是因为**假后端证明不了超时**：`/compare` 在后端要真跑一遍全量检索，
  给它单独留了 120 秒超时 —— 而假后端是睡 400 毫秒返回，20 秒都绰绰有余。
  这个教训阶段一已经付过一次学费（钉住实验 19~26 秒 vs 前端 20 秒超时 →
  一个完全正常的实验必然报超时，而假后端把问题掩盖到了真后端）。
  **对齐实验更进一步**：它比 `/compare` 重约 4 倍（5 个变体 × 3 路检索 = 15 次全量评测），
  所以它有自己的 **180 秒**超时（`RAG_ALIGN_TIMEOUT_MS`）—— 同一个面板里的不同端点，
  超时值各自按自己的固有耗时定，不套用别人的。

## 第五种模式：Agent 工具调用（会调模型 · 自主选工具）

前四种要么是"一次调用长什么样"（流式 / 结构化）、要么是"运行时事实"（线程与预算）、
要么是"离线链路"（RAG，调模型 0 次）。
**第五种是唯一一个"会调模型、还会自己决定调哪些工具"的模式** ——
所以它回答的问题也换了一层：不是"这次调用成不成功"，
而是**"它为什么选这个工具、失败在哪一步、花的钱值不值"**。

| 部件 | 端点 | 它证的是什么 |
|---|---|---|
| 跑一个任务 | `POST /api/agent/ask` | **本页唯一的写操作，会真的花钱**（`AGENT_ASK_TIMEOUT_MS` = 180 秒）。返回答案 + 每一步 + 每次工具调用 + token 成本。**本次新增两个必填前提**：`workspaceDir` + `permissionLevel`（见下一节） |
| 历史运行 | `GET /api/agent/runs` | 每次任务都记在库里。含状态、token、工具次数、**失败细分**，以及本次新增的**权限档位**一列 |
| 运行详情 | `GET /api/agent/runs/{id}` | 还原这一次的执行过程：每步的检查点大小 + 每次工具调用（含"计入熔断"那一列）+ 回显本次的**执行前提** |
| **五层 trace** | `GET /api/agent/runs/{id}/trace` | **第十三轮新增**：会话 → 运行 → LLM 调用 → 工具调用 → **检索** 五层完整还原（详见下面那一节） |
| 四层保护 | `GET /api/agent/limits` | 并发闸门 / 排队超时 / 熔断的当前状态（**全局共享**，不是某次运行的属性） |

### 发起任务的两个前提：工作区目录 + 三档权限

「跑一个任务」那张卡片最上面是两个**执行前提**（在提问框下面、两个归因输入框上面）：

| 控件 | 必填 | 它决定什么 |
|---|---|---|
| 工作区目录 | **是** | 后端在**动模型之前**校验它真实存在且确实是目录。目录不存在 ⇒ 当场拒绝、**不花钱**、不留运行记录。它当前**不改变任何工具的行为**（本项目没有文件工具），而是权限判定的依据与落库的审计字段 |
| 权限 | 否（默认最严的一档） | 读操作在任何档位下都直接执行；**写操作**在「仅可查看」/「工作区内修改」下停下来等人点头，在「完全权限」下**直接执行、不产生审核请求** |

#### 三档为什么各自挂一句"会发生什么"，而不是三个标签

因为**中间那一档在当前功能下与「仅可查看」行为完全相同**：本项目的 6 把工具没有路径参数，
判不出"这次写在工作区内还是外"。只给三个名字的话，使用者会以为「工作区内修改」已经放宽了什么 ——
于是他会选一个自己以为更宽的档位，然后对"怎么还在弹审批"感到困惑，
而那个困惑最后会被归因成权限功能坏了。所以三档的说明**如实写**，包括那一句"当前行为相同"。

默认值是「仅可查看」——一个"默认就能跳过人工确认"的界面，会让那条最重要的人工闸门在多数运行里都不生效，
而它失效时**没有任何报错**。

#### 工作区目录为什么只能是一个"能填的输入框"

后端要的是一个**当前机器上真实存在的目录**，而浏览器**给不出本机路径**
（`<input type="file">` 只给文件名、`showDirectoryPicker` 拿到的是句柄且默认不可见路径）。
所以这里只能让人自己填或粘一个路径 —— 把它做成"看起来能选目录"的假控件，
会让人以为选完了、实际什么都没传。默认值给 `.`（Java 进程的工作目录）：
它是唯一一个在任何机器上都存在的目录，而写死一个绝对路径会在别人的机器上必然失败。

#### 「完全权限」必须能被看见（四处都写出来）

那一档下写操作**不产生审核请求**，于是"审批记录为空"这件事多出了第二种含义 ——
原本只有一个读法（"这次没有需要确认的写操作"），现在还有"**它做了但没人被问过**"。
两者在数据上完全一样，而含义正好相反。所以：

1. **结果卡与运行详情**各回显一行「执行前提：完全权限 · D:\work\...」（显示的是**服务端实际用的那一份**，
   不是界面上刚填的那份 —— 目录被规范化过）；
2. **历史列表**多一列「权限」，`FULL_ACCESS` 是**红标签**；
3. **运行详情里的「人工确认（HITL）」那一节**：空列表 + 完全权限时给的是**警告条**
   （"这张表为空**不能**读成「这次没有写操作」"），而不是那句"没有触发人工确认"；
4. **五层 trace** 的 `notes` 里有一条同样的说明。

#### 界面自检为这两个参数钉了什么

除了"两个控件存在"，还钉了三条更值钱的：

- **三档的后果文案如实**（尤其"工作区内修改与仅可查看当前行为相同"这一句不能省）；
- **默认档位是最严的那一档**（读 `input[type=radio]:checked`，不是读文案）；
- **出站请求体里真的有 `workspaceDir` 与 `permissionLevel`** ——
  "页面上有这个框"证明不了"它被发出去了"，中间隔着一次字段名拼接，
  而字段名写错的症状是：后端认为没传 ⇒ 走默认值（无工作区 + 仅可查看）⇒ **界面上一切正常**。

另外断言了**结果卡回显「执行前提」那一行**：它证明的是"服务端实际用的那份前提被显示了"，
而不只是"界面上有这个控件"。

### 这一页刻意做的四件事

1. **答案与过程同屏**。只显示答案的话，"查了 3 次、失败 2 次、最后蒙对"与"一次就答对"
   长得一模一样 —— 而区分这两者是这个功能的全部价值。核心视觉是**执行过程的时间线**
   （think → act → observe），不是汇总表：表格擅长横向比大小、不擅长讲顺序，而"为什么"是顺序性的。
2. **每次工具调用都显示 `stage` + 参数 + 回填文本**。`stage` 说明"死在哪一步"，
   回填说明"模型当时看到了什么"。`stage` 用中文短语显示，但**枚举名放在 `title` 里** ——
   排查时要能和日志里的字样对上。
3. **被拒绝的调用也在页面上**。报告要回答"模型想调几次、其中几次没让它调"，
   只显示成功的会让这个数字永远偏小。
4. **限额块写明"全局共享"**。闸门与熔断是全局的（同一把工具被所有任务共用），
   放进某次运行的详情里会让人以为是那次的属性。

### 界面上不下判断（判据只能有一份）

「计入熔断」这一列由**后端**给（`ToolCallStage.countsAsToolFailure()`），前端不自己判 `stage` 的好坏 ——
那会让判据变成两份（另一份在 `CircuitBreaker` 里），而两份必然漂移，
漂移之后的现象是"页面说工具没事，但熔断其实已经打开了"。

同理，限额块只把**实际值与阈值并排**显示（`0.75 / 0.5`），不替读者下"高不高"的结论。

### 这一页抓出来的一个真 bug（值得单独记）

真后端上这一页一直显示"模型侧并发闸门未启用" —— 也就是说**上一轮做的模型侧限流
在真实路径上压根没生效，只在当时那批后端测试里生效**（那批测试已随后端整体删除）。
根因是 `OpenAiModelTurn` 上同时有
`@Component` 与 `@Bean` 两个 bean 定义，条件装配看到组件扫描那个就跳过了 `@Bean` 方法
（含外层包装）。它不报错、不抛异常，唯一表现就是"某个能力没生效"。

**如果没有这一页，这个 bug 会一直躺到有人真的做压测才发现。**

### 自检为什么分两条路径断言

| 路径 | 能验证什么 |
|---|---|
| 假后端 | 一条刻意的四步轨迹（列目录 → **编错工具名被拒** → 改对 → 作答），可确定性断言完整过程 |
| 真后端（假 key） | 模型调用 401 → 那次运行**一步都没有**，时间线不渲染。所以这条路径验证的是**另一件更有价值的事**：失败被分类成 `UPSTREAM_AUTH` 并给出"重试没有意义"的建议 |

这不是"把断言放宽"，而是两条路径本来就跑在不同场景里。
硬等 `.agent-timeline` 会让真路径必然超时，而失败原因看起来像"界面没渲染"。

## 第五种模式的第六张卡：五层 trace（第十三轮）

点开一次运行之后，**运行详情下面**多出一张卡：把这次运行按
**会话 → 轮次/运行 → LLM 调用 → 工具调用 → 检索** 五层完整还原。

### 它为什么与"运行详情"并存，而不是把那张卡改大

| 卡 | 回答什么 | 端点 |
|---|---|---|
| 运行详情 | 这次运行**怎么样**（状态 / 答案 / 每步 token / 每次工具调用） | `/runs/{id}` |
| 五层 trace | 这次运行**到底发生了什么**（五层对齐 + 会话 + **检索明细** + 金额 + 提示词指纹） | `/runs/{id}/trace` |

两个端点代价不同（后者要读五张表 + 算金额），**失败也要能分开看** ——
所以它们在 `useAgent` 里是**两个独立的 Remote 态**，两个请求**并发发**（都用 runId，没有数据依赖）。
合成一个的话，"trace 读不到"会让整个详情页变成错误态，连状态与答案都看不到 ——
而这一页正是排查入口（"用户说这次答得不对"时打开的就是它）。

### 检索那一层：它在此之前"看起来有了"，其实什么都没有

这是这张卡存在的**唯一理由**，值得说清。在第十三轮之前，`search_docs` 的命中结果
**一直记着** —— 记在 `agent_tool_invocation.feedback` 里，是一段这样的中文回填：

```
在 516 个文档片段里找到 3 条相关内容（按相关度排序）：
[1] 章节：Java 开发者 → AI Agent 岗位 · 专属路线 > 七、周计划（10 周，每周 10–15 小时） > 阶段二（2–4 周）RAG —— 重点在「定位问题」而非「跑通 Demo」
    来源：roadmap-java-to-agent.md  估算 203 token
    内容：分块：语义段落 / 标题层级切分 + Overlap，别按固定字数硬切……
```

看起来什么都有。但**"在那段文本里"与"在数据里"是三件不同的事**：

| 问题 | 在那段文本上只能怎么做 |
|---|---|
| 这次任务一共检索了几次 | 数出现了几次「在 516 个文档片段里找到」 |
| 命中的是哪几个块 | 正则解析那段中文（章节名里还有 `>` 与空格） |
| **检索塞进 prompt 的 token 有多少** | **做不到** —— 每块的 token 有，但"这一次检索一共占多少"没有任何地方给 |

所以现在落成 `retrieval_call` + `retrieval_hit` 两张表，卡片上画成一张命中表：
**名次 / 得分 / 来源+章节 / 每块 token / 片段开头**。
判据值得记：**问"我要的那个数能不能从已存字段直接读出来"，而不是问"这件事有没有被记下来"**。

### 卡片上三处刻意这么画的地方

1. **五层到场清单排在最上面**。理由与"待确认卡排第一"同一条：它是**读这一页之前必须先知道的事**。
   不看它就直接往下读，会把"这一层本来就没内容"误读成"漏记了"。
   标签的颜色编码的是**后端的 `expected` 布尔**，不是"有没有内容" ——
   一次没调工具的运行，第 4、5 层**本来就该是空的**（正常）；
   而一次调了检索却查不到明细，那个空是**缺陷**。两者在页面上长得完全一样，所以让后端把判断说出来。
2. **检索 token 必须标成「估算」**。它来自块自带的 `TokenEstimator` 计数，
   而账目口径的 token 来自上游 `usage` —— 两个口径混在一张页面上而不加区分，
   等于把估算当事实记账。接口里也显式给了 `hitTokensEstimated: true`。
3. **金额那一格的纪律与成本看板一字不差**：算不出来就显示「算不出金额」+ 原因，
   **绝不给 ¥0.00** —— 那个 0 会被读成"这次不花钱"，而真相是"我们不知道它花多少"。
   界面自检里有一条断言专门钉这个（`trace-cost-unknown` 存在时，页面上不许出现 `¥0.00`）。

### 这一页新增的断言里，哪几条是真在钉性质

```bash
pnpm mock && pnpm dev:mock          # 终端 A、B
UI_URL=http://127.0.0.1:5173 pnpm check:ui
```

- **「命中的块逐条列出（不是一段文本）」** —— 一个只把 `feedback` 印出来的实现会过不了这条，
  而那正是这张卡要消灭的形态；
- **「名次从 1 开始且连续」** —— 后端在写库时把名次与列表顺序对齐，这里钉住它在页面上的样子。
  两边都钉住才叫闭环：只钉后端的话，"页面按数组下标重新编号"这种错不会被发现；
- **「每一层的标签与后端给的 expected 自洽」** —— 用 `data-expected` 与标签文案交叉验证，
  任何"空 / 该有"分不开的渲染都会红；
- **「关掉详情后 trace 卡一起消失」** —— 不消失的话，"关掉再点另一次运行"的瞬间会先渲染出
  上一条运行的 trace，而那种"闪一下旧数据"在排查时会被读成"这次运行查到了那些东西"。

### 假后端里的假数据刻意造了三件事

`mock/agent-routes.mjs` 的 `traceFromScript()`：① 一次**正常的**检索（5 条命中里给 3 条，名次 1/2/3）；
② 一次 **0 命中**的检索（`hitCount=0` 但 `query` 与 `indexSize` 都在）；
③ 一条**只列文档、不检索**的路径（第 5 层 `expected=false`）。
另外它把 `cost.amount` 写成 **`null`** 而不是一个数字 ——
假数据里写个金额的话，那面"算不出来就说算不出"的红旗就永远没机会被自检看到。

> ⚠️ 与 `/runs/{id}` 那条注释同一个坑：**假数据的形状必须与后端逐字段一致**，
> 而且这几条 route 必须注册在更宽的 `startsWith('/api/agent/runs/')` **之前** ——
> 否则 `runId` 会变成 `${id}/trace`，详情端点收到一个带斜杠的 id。

## 第五种模式的另一半：人工确认（HITL，第九轮）

「Agent 工具调用」现在有**五张卡**，排第一的是**「待我确认」**——
它不是"再多一块信息"，而是全页**唯一有截止时间、并且正在阻塞别人**的东西。

### 它为什么必须排在"跑一个任务"上面

后端上，一次高危写操作（本项目的 `propose_review`，会真的建一条记录）走到门禁 ⑤ 时
会**把当前线程停住等人**（最长 `ai.agent.approval.timeout`，默认 120 秒）。
等不到就**按拒绝处理**。

也就是说：**"这一块没刷新"的后果不是"看到旧数据"，而是那个任务会一直等到超时然后失败** ——
人明明坐在页面前，却因为它没显示而白等一场。
所以它的优先级高于"跑一个任务"（那个只是花钱，不会自己失败）。

### 为什么它是整个界面里唯一**轮询**的地方

这个项目在别处都刻意避免轮询（进面板拉一次、点刷新再拉一次）。
待办列表是唯一的例外，因为它有上面那个性质：**有人在等它**。
一句话概括这两者的差别：**别的块是"用户想看才拉"，这一块是"不拉就会出事"**。

`useAgent` 里的三条纪律把轮询的代价按住：

| 纪律 | 不这么做的后果 |
|---|---|
| **只在面板激活时轮询**（`active` 为 false 就清掉定时器） | 切走之后还在后台打请求；而且 StrictMode 下 effect 挂两次，不清理会留下**两个**永不停止的轮询 —— 它不报错，只是偷偷多打一倍 |
| **不重叠**（`polling` ref 守卫，上一次没回来就跳过这一轮） | 慢响应会叠成一串并发请求，而它们的结果**乱序**返回 —— 界面上会出现"刚决定的又变回待办了"，且只在网络慢时复现 |
| **失败时保留旧数据**，只记一个标记 | 一次临时失败把待办区清空，会让人以为"待办没了"，而**那个任务还在那里等人并倒计时** |

间隔是 `AGENT_APPROVAL_POLL_MS = 2500`。取值要同时满足两头：太长等于人看到待办的延迟
直接变成任务的额外等待；太短则是在人盯着不动时白烧 CPU 与日志。

### 卡片上的五件事，各自为什么必须有

1. **参数原样显示**（不折叠成摘要、不脱敏）—— 人批的**就是这份参数**。
   后端为此刻意不做加工（见 `ToolApprovalRecord` 的注释），界面折起来"帮你省地方"
   就等于让人凭标题批准一个他没看清的操作。
2. **「已等 Ns · 还剩 Ns 就按拒绝处理」** —— 审批对任务耗时的影响，唯一可量化的口径就是它。
   剩余不足 1/4 或 15 秒时整条变红底（`.is-urgent`）：**这一条的存在理由是"它自己会失败"，必须一眼可见**。
3. **风险声明**（例如「写（非幂等，需人工确认），可能破坏性」）—— 来自工具的 `ToolHints`，
   与"要不要审批"的判据**同源**。页面不自己判这条该不该批。
4. **「谁做的决定」是每条自己的输入框**，不是全局一个。
   共用一个会让"写给 A 的理由"跑到 B 上，而且**不会报错** —— 它只是把一条错误的理由记进了真实的审计记录。
5. **「拒绝」不是一键动作**：第一次点只展开理由框，第二次点才提交。
   拒绝理由会**原样回填给模型**，是模型换方案的唯一依据；
   一键拒绝会稳定地产生一堆"没有理由的拒绝"，而那种审计记录几乎没有价值。

> 视觉上一个刻意的选择：**「批准并执行」不用 primary 样式**，也不给拒绝预填理由。
> 列表本身对"批"是有吸引力的（点一下就继续），所以界面不该再加强它 ——
> 也不该诱导任何一个方向。

### 决定之后的结论条：为什么不写"操作成功"

「决定生效」与「任务继续」是**两件事**，而它们的组合有三种含义完全不同的处境：

| `awakened` | `resumed` | 含义 |
|---|---|---|
| true | — | 有线程正在等 → 任务**当场继续跑完**（正常路径） |
| false | true | 没人等了（进程重启过 / 客户端断开）→ 后端**从检查点接着跑**起来 |
| false | false | 决定已记录，**但任务还停着** —— 这一种最需要人去处理 |

把这三种压成一句"操作成功"，第三种就会被当成正常。
所以结论条把这两个布尔**连取值一起显示出来**。

### 界面上不下判断（判据只能有一份）—— 这次又多了一处

「等人工确认 / 人工拒绝 / 等确认超时」三个新 stage 的中文说明写在 `STAGE_META` 里，
但**枚举名放在 `title` 属性里**（排查时要能和日志里的字样对上）。
而"这一条该不该批"完全不判 —— 那是 `ToolHints.requiresApproval()` 的事。

一个新增的界面文案纪律：**「超时」与「人工拒绝」刻意分开显示**。
它们对执行是同一个结果（不执行），但要通知的人完全不同 ——
前者是**流程没接上**（审批通知发到哪了、为什么没人看到），后者是**业务判断**（他为什么不同意）。
合并之后，一个"审批流压根没接上"的系统会表现得像"业务上一直不同意"。

### 空列表必须被解释（三种原因，别混起来读）

「当前没有待批」有三种完全不同的原因，混起来读会得出**相反的结论**：

1. **确实没有危险操作** —— 本项目的三把只读工具（检索 / 列目录 / 读章节）都是只读声明，按规矩不需要审批；
2. **那个写操作还没被发起** —— 只有模型真的决定要建工单时才会出现待批；
3. **闸门被关掉了**（`ai.agent.approval.enabled=false`）—— 这时页面上会**明确弹出警告**。

第 3 种是最危险的一种误读：**"闸门没装"看起来像"系统很安全"**。
这正是「卡片在」不等于「列表有行」的形状（「『已完成』这个状态，只在被实际问过一次『装的是哪个实现』之后才算数」），
所以界面上必须把闸门开关状态**单独显示出来**，而不是靠"待办列表为空"去暗示。

> 打真后端时，自检验证的正是这一半（真后端上没有待批，因为没有真 key 跑不出写操作）：
> 空列表里那三句解释、以及闸门的当前状态，都必须渲染出来。

### 运行详情里的「人工确认（HITL）」一节

点开某次历史运行，会多出一节回答**「这次任务里人一共被问过几次、各等了多久、谁批的」**。

它挂在**运行详情**里而不是只靠那张待办列表，因为待办回答的是**当下**（"现在要我批什么"），
而这里回答**历史**。那句验收原话是「什么时候让人确认」——
而"什么时候"只有挂在那次运行的时间线上才有意义（第几步、等了多少秒）。
合并成一个列表的代价很具体：人分不清"这条是要我处理的"还是"这条是已经处理过的"。

### 假后端的审批状态机（为什么它比别处的假数据复杂）

别处的假数据都是"每次都返回同一份"，HITL 不行 —— 因为自检要验证的是一条**状态转移**：
点「批准」→ 那条待批从列表里消失、**并且下一次 `/ask` 返回的轨迹是"写操作执行成功"**。

所以 `mock/agent-routes.mjs` 里带一个极小的状态机（`approvalState`），并多两个**只有假后端有**的端点：

| 端点 | 作用 | 为什么需要 |
|---|---|---|
| `POST /api/agent/__reset-approval` | 把状态复位成"有待批" | 一次自检里要走完**两条相反的分支**（批准 / 拒绝）。只测一条的话，「拒绝之后那个副作用真的没发生」这条最重要的结论就没人验证 |
| `POST /api/agent/__set-approval` | 直接落一个决定（绕过界面） | 自检最后还要验证"批准之后的完整四步轨迹"，而那时界面已经停在"已拒绝"上了。再点按钮会触发真后端的"不能重复决定"守卫 |

**形状仍然是照真后端写的**：状态取值（`PENDING`/`APPROVED`/`DENIED`/`TIMED_OUT`/`EXPIRED`）、
字段名、字段类型全部一致。真后端上这两个路径会 404，所以自检只在假路径调它们。

> 这里踩过一次值得记的坑：**第一版把 `approvals` 字段塞进了 `run` 对象里**
> （`detailFromScript(..., { approvals })` 的 overrides 是展开到 `run` 上的），
> 而真后端放在**顶层**、前端也读顶层。
> 结果是界面永远显示"这次运行没有触发人工确认"，而假数据里明明有审批记录 ——
> 失败信息看起来像"详情页没渲染审批历史"，排查方向会跑到组件上去。
> **形状不一致的假数据比没有假数据更坏**：它让自检红在一个与真实代码无关的地方。

## 与后端的契约

### 流式：`POST /api/chat/stream`

请求体 `{"conversationId":"...","message":"...","temperature":0.3}`，
响应 `text/event-stream`，三种事件：

| 事件 | data | 前端处理 |
|---|---|---|
| `content` | JSON `{"delta":"..."}`（**不是纯文本**，原因见下） | 拼到当前气泡 |
| `done` | JSON 用量 `{promptTokens, completionTokens, totalTokens, model}` | 显示在气泡下方 |
| `error` | JSON `{"message":"..."}` | 红色 Alert 展示；**超时**类错误额外给「重试本轮」按钮 |

> **为什么 `content` 也要包 JSON**：Spring 写出的是 `data:xxx`（冒号后**没有**分隔空格），
> 而 SSE 规范要求客户端「若值以一个空格开头，吃掉那一个空格」。两条规则一撞，
> 任何以空格开头的增量分片都会**丢一个空格**——实测模板渲染成 `publicFlux`（应为 `public Flux`）。
> 包成 JSON 后 data 以 `{` 开头，空格被引号保护，两种服务端写法都不会再被吃掉。

### 结构化：`POST /api/chat/structured`

请求体 `{"conversationId":"...","question":"..."}`，响应：

```jsonc
{
  "answer":   { "answer": "...", "confidence": 0.92, "keywords": ["SSE", "..."] },
  "attempts": [                                  // 每一轮尝试的完整留痕
    { "index": 1, "rawOutput": "{...}", "parsed": null, "issues": ["字段 confidence：..."], "elapsedMs": 1180 },
    { "index": 2, "rawOutput": "{...}", "parsed": { /* ... */ }, "issues": [], "elapsedMs": 940 }
  ],
  "degraded": false                              // true 时 answer 是后端兜底文案，不是模型给的
}
```

**`attempts` 是这张卡片的主角**：结构化输出真正值得看的东西是「模型第一次错在哪、
回灌之后改对没有、最后是不是降级了」—— 只显示最终答案是看不出这些的，
而这个功能的全部价值恰恰在那条链路上。所以界面上它是默认展开的（只要发生过回灌或降级）。

一个界面上的诚实标注：**置信度是「模型自己报的」，不是系统评估的可信度**。
它只用来触发「不确定」协议（低于阈值会被判不合格并回灌重答），不要当成质量指标看。
文案里显式写了这一点，否则很容易被误用。

## 几个刻意的设计决定

1. **用 `fetch` + `ReadableStream`，不用 `EventSource`**：`EventSource` 只支持 GET，`message` 就得塞进 URL（长度限制 + 明文进访问日志），还不能带自定义 header，且断线会自动重连导致重复请求。
2. **增量渲染按 `requestAnimationFrame` 合并**：一个 token 一次 `setState` 会让长回复重渲染上百次，叠加 Markdown 解析直接卡顿。现在每帧最多渲染一次。
3. **Markdown 渲染做双保险**：`markdown-it` 关掉 `html`（第一层），渲染结果再过 `DOMPurify`（第二层）。模型输出是不可信输入，`dangerouslySetInnerHTML` 不能裸用。
4. **`conversationId` 每次「新会话」都换**：后端按它做对话记忆，沿用旧 ID 会把上一轮上下文带进来。
5. **`crypto.randomUUID` 有兜底**：它只在安全上下文（https / localhost）可用，内网 `http://192.168.x.x` 部署时会 undefined。
6. **`highlight.js/lib/common`**：引默认入口会把 190+ 种语言全打进包，产物从 1.6MB 掉到 600KB 级别。
7. **结构化模式的 temperature 滑块直接不显示**（而不是置灰）：后端为了输出稳定把它钉在 0.0，给一个拖了不生效的滑块比不给更糟 —— 用户会以为自己的调整没起作用，然后开始怀疑整个功能。
8. **原始输出用 `pre` + `white-space: pre-wrap`**：结构化输出的 JSON 经常是单行几千字符，不换行会横向撑破卡片、让整页能左右滚动 —— 展示模型原始输出时最容易忽略的一点。
9. **`vite.config.ts` 里关掉了监听对 `.*.tmpdir/` 的遍历**：编辑器/工具落盘时是"写临时文件 → 原子重命名"，Windows 上那个瞬间出现又消失的临时文件会让 chokidar 抛 `EBUSY`，而 **Vite 没有捕获它 —— 整个 dev server 直接退出**。表现是"改一个文件，前端服务就没了"，很容易被误判成代码写崩了。踩过一次，故显式 ignore。

## 超时（三道，必须与后端联动）

| 超时 | 默认值 | 防的是什么 |
|---|---|---|
| 首字节 | 30s | 后端没启动 / 模型一个字都不回 |
| 空闲 | 30s | 回答到一半连接断了（TCP 半开、代理静默丢包时**不会报错，只会没数据**） |
| 整体 | 180s | "每 29 秒来一个字"把页面无限期占住 |

> **超时必须大于后端的重试预算**（后端首字超时 20s + 退避 ≈1.1s）。前端先超时会让用户看到
> "失败"，而后端其实正在成功返回的路上 —— 这种假故障最费排查时间。
> 反过来前端超时也必须存在：后端进程被 kill、防火墙静默丢包时，只能靠前端自己把"卡住"变成"明确失败"。

**实现上有一个坑：fetch 的 body 流不响应 `abort()`。** abort 只中断请求本身（连接、响应头阶段），
流已经开始后 `reader.read()` 正挂起等待时，abort 不会让那个 Promise 落地 ——
靠 `setTimeout(() => controller.abort())` 做超时，结果是超时后页面永远停在「正在思考…」。
所以帧级超时做成了"与 `read()` 赛跑"（见 `src/api/sse.ts` 的 `waitForRead`），
整体超时才用 abort（并单独标记，避免和用户点「停止」混为一谈）。

> 结构化端点**不需要**这套：它没有长连接，超时也是一刀切，所以 `api/structured.ts` 里
> 用最朴素的 `AbortController` + `setTimeout` 就够了。**照抄流式那套反而是错的。**


把 `dist/` 内容拷进 `ai-agent/src/main/resources/static/` 即可同源访问（连 CORS 都不用配）。

> 该行为**尚未实测**（没机会跑到那个时长），属于已知未验证项。

## 第六种模式：成本看板（只读聚合 · 不估算 token）

前六种模式回答的都是**「这一次怎么样」**：一次调用长什么样、一次任务绕了几圈、
一次实验哪组更好。成本看板是**回头看**的那一页，它回答三个问题：

| 问题 | 页面上的哪一块 |
|---|---|
| **花了多少** | 头部合计 + 「按天」表 |
| **谁花的** | 「**按租户**」（谁的钱）+「按业务归因」（哪个功能）+「按模型」三张表 |
| **花得值不值** | 失败的运行数、缓存命中率、「按工具」表、口径对账 |

第三问是这一页与**账单截图**的区别：账单只知道花了多少，而
「花了钱又没办成事」（`status=FAILED` 的运行）只在我们自己的数据里才有。

⚠️ **「按租户」与「按业务归因」是两栏、两个维度**（不是同一栏的两种排法）—— 见下面那一节。

### 端点

| 端点 | 回答什么 |
|---|---|
| `GET /api/cost/summary?days=7` | 看板快照：合计 / 按天 / **按租户** / 按业务 / 按模型 / 按工具 / 对账 / 备注 |
| `GET /api/cost/prices` | 价格表 + 「还缺哪些模型的价格」（一份能照着做的待办） |

### 这一页最重要的一条纪律：**不显示我们算不出来的东西**

`amount` 是可空的，null 有两种含义（**价格没配** / **模型没上报**），
两种都带着 `amountReason`。界面**绝不允许**把 null 渲染成 `¥0.0000`：

- `¥0.0000` 会被读成「这个功能不花钱」；
- 而真相是「**我们不知道它花多少钱**」。

这两句话对使用者的含义完全相反，而界面上长得一模一样。
所以假后端的数据里**刻意留了一个没有价格的模型**（`deepseek-v4-pro`，
它的 token 计入总量、不进金额），自检里那两条断言专门盯着它：
页面上必须出现「算不出」+ **可见的原因**，而合计必须被标成**下界**。

> 顺带两条实测细节，改这块之前值得知道：
> ① **原因必须显示出来，不能只放进 Tooltip** —— 「为什么算不出」就是那一格的全部信息，
> 隐藏的信息只有已经知道它存在的人才会去找；
> ② 给 antd `<Tooltip>` 的直接子元素传 `title`，**那个 title 不会落到 DOM 上**（Tooltip 会吃掉它）——
> 自检里第一版断言"元素带 title 属性"因此是红的，而功能其实在。

### 金额是"按模型分别算完再相加"

一天里跑过多个模型时，`当天总 token × 某一个单价` 是**错的** ——
而它给出的钱数看起来完全正常。所以：

- 钱只在**单一模型**的粒度上算（那是唯一有确切单价的粒度）；
- 「按天」「按业务」的钱 = 把当天的每个模型分别算完再相加；
- 「按业务」那一栏因此**不给单一金额**，而是写明"去按模型那一栏看"——
  说清了读者就会去核对，不说就会被当成一个真数字。

同理，**「按工具」那一栏没有金额**，这是刻意的：token 花在**模型往返**上，
工具消耗的是延迟与下游容量。"这把工具花了多少钱"只能靠"它让模型多跑了几轮"间接归因，
而那是**推测**，不是数据。

### 口径对账（看板自己的仪表自检）

看板的钱按**步骤表**（`agent_step`）汇总，而运行列表显示的是
`agent_run.total_tokens`（循环自己累加的、也决定 token 上限）。两者本该一致 ——
**不一致说明有一处漏记**，而看板上完全看不出来（只是钱多一点或少一点）。
所以页面上把两个数字并排摆出来，让不一致自己现形。

### 价格怎么配

价格来自**上游的商业条款**，代码里刻意不写死默认值。在 `application.properties` 里加：

```properties
ai.cost.prices[0].model=你的模型名
ai.cost.prices[0].input-per-million=未命中缓存的输入单价
ai.cost.prices[0].cache-hit-per-million=命中缓存的输入单价
ai.cost.prices[0].output-per-million=输出单价
ai.cost.prices[0].currency=CNY
ai.cost.prices[0].effective-from=2026-01-01
ai.cost.prices[0].source=价格出处
```

**两个容易搞错的地方**：

1. **缓存价要单独配**。命中与未命中的价差是数量级级的，不配它的后果不是报错，
   而是成本**稳定高估**，且高估的倍数随上游缓存命中率浮动 —— 一个我们看不见也调不了的量。
   不配时按未命中价算（偏保守），页面上会把这一档标成「**假设**」而不是「事实」；
2. **调价要新增一条带新 `effective-from` 的规则，不要改旧的那条** ——
   否则历史成本会被新价改写，而那种改写**不留任何痕迹**。

### 两个归因维度：租户（谁的钱）与业务（哪个功能）

成本看板上有**两栏**，而它们是两个独立的分组，不是同一栏的两种排法：

| 栏 | 回答 | 唯一的写入方 | 空值叫 |
|---|---|---|---|
| **按租户** | **谁**在花钱 | Agent 面板上的「**租户**」输入框 → `agent_run.tenant_id` | 「未标注租户」 |
| 按业务归因 | 花在**哪个功能**上 | Agent 面板上的「**业务归因**」输入框 → `agent_run.intent` | 「未标注」 |

**为什么不合成一个输入框**（`京东-客服问答` 那种拼法）：两个后果都不报错 ——
① "按租户看一共多少"会退化成前缀匹配（`LIKE '京东-%'`），一次拼写不一致就让同一个租户
**裂成两行**，而两行加起来才是真相；② 租户改名、或一个问题换业务归属，
都要去改历史数据，而历史是只追加的。

**两栏的金额是"按 token 占比从合计分摊"来的**（后端 `CostDashboardView.allocateByTokenShare`）。
费用对 token 是线性的，所以这与"逐模型算完再相加"**等价** ——
这也解释了为什么两栏各自加起来都等于「按模型」那一栏的和（自检里有一条断言钉着它）。
后端的每一行都带 `amountBasis`：`PER_MODEL`（直接算出来的）或
`ALLOCATED_BY_TOKEN_SHARE`（分摊的）—— 两种金额在页面上一模一样，但含义不同。

**「未标注」/「未标注租户」永远单独占一行**，不会被并进任何一组里 ——
并进去会让那一组的成本虚高，而虚高的部分无从发现。
⚠️ 两栏的空值**刻意用了不同的词**：它们处置方式不同（让调用方传 `tenantId` / 传 `intent`）。


## 第七种模式：Prompt 版本（**唯一会改"前面这些页面的行为"的一页**）

前六种模式都在回答"**这一次**怎么样"：流式怎么推、结构怎么校验、线程怎么排队、
检索找不找得到、Agent 为什么这么选、这一批花了多少钱。
第七种不一样 —— 它管的不是一次调用，而是**以后所有调用的指令**。

这一点决定了它和别的页面的三点不同：

1. **改动的生效范围是全局的**：换一版提示词，下一次 Agent 运行 / 下一轮对话就是新指令。
   所以它的两个写动作都带"这会影响什么"的说明（见下面"存 ≠ 生效"）；
2. **改坏了不报错**：别的页面的输入错误都会立刻现形（400、校验失败、JSON 解析不了）；
   而提示词写坏了，接口 200、模型照样回答、字数甚至差不多，**唯一的症状是答案质量下降**。
   所以这一页有一整套写入前校验（`PromptValidator`）；
3. **它是唯一需要"回滚"的一页**：其余页面的操作都是只读或者一次性的，
   而这里的每一次改动都在改变系统行为 —— 阶段四的验收口径正是
   「Prompt 改坏**能回滚**」。

### 端点（6 个）

| 方法 | 路径 | 回答什么 |
|---|---|---|
| GET | `/api/prompts` | 有哪几份提示词、各自生效的是哪一版、热更新的边界 |
| GET | `/api/prompts/{kind}/versions` | 这一份的全部版本（版本号降序） |
| GET | `/api/prompts/{kind}/versions/{n}` | 某一版的正文 |
| GET | `/api/prompts/{kind}/diff?from=&to=` | 两版之间改了什么（**省略 from 时自动取"上一版 → 最新版"**） |
| POST | `/api/prompts/{kind}/versions` | 存一版新的（**不生效**） |
| POST | `/api/prompts/{kind}/activate` · `/rollback` | 让某一版生效 / 回滚到某一版 |

三种失败对应**三个不同的状态码**，因为"接下来该做什么"完全不同：

| 场景 | 码 | 使用者该做什么 |
|---|---|---|
| 名字拼错 / 版本不存在 | 404 | 改请求 |
| 正文不合规（空、超长、围栏不配平、缺锚点、没写说明） | 400 | 改内容 —— **重试同一个内容永远不会成功** |
| 切换的前提已过期（别人先动手了） | 409 | **刷新后重试是有意义的** |

全回 500 的后果很具体：使用者以为"系统坏了"，然后反复重试同一个请求。

### 这一页最重要的三条纪律

#### ① 「存」与「生效」是两个动作，而且保存后必须明说"尚未生效"

一次粘贴失误不该直接作用到线上。先存、看一眼篇幅与内容、再决定要不要让它生效 ——
这样**退路出现在生效之前**。（"保存后忘了激活"是可见的：列表里那一版不显示「生效中」；
而"自动生效"造成的是一次真实的线上变更。两种失误的代价不对称。）

#### ② 回滚是**新增一版**，不是把指针挪回去

回滚的正文复制自旧版，`forked_from` 记着来源，落成界面就是那一行
「**复制自第 N 版**（回滚产生的新版本）」。

为什么不做成"把指针挪回去"：那会让**这次回滚本身**从历史里消失 ——
事后只会看到"第 5 版之后又出现了第 3 版的内容"，而"是谁、什么时候、把哪一版拉回来的"查不到。
这与成本看板那条"**调价要新增一条、不要改旧的**"是同一条纪律：
**会改写历史的操作，事后无法解释。**

> 顺带一个边界：如果当前生效版的内容**已经与目标版逐字节相同**，这次回滚是 **noOp**
> —— 不新增版本，但接口会明确回 `noOp: true` + 一句"没有新增版本"。
> 不写清楚的话，"没产生新版本"与"回滚失败了"在屏幕上一模一样。

#### ③ 校验分**拒绝**与**警告**两级，而警告必须显示

- **拒绝级**（写不进去）：正文为空、超长、``` 围栏不配平、结构锚点缺失、改动说明没写。
  这几条都对应**真实的、不报错的事故形态**（粘贴被截断、只复制了其中一段）；
- **警告级**（写得进去，但页面必须显示）：篇幅低于下限、相对上一版骤减/暴涨。

为什么不能只有拒绝：**提示词改坏最典型的形态恰恰是"内容有效但少了一段"**，
而那类改动在拒绝级判据下全绿。反过来，把可疑的都变成拒绝也不行 ——
误拒会逼人去绕过校验，而**一个被绕过的校验等于不存在**。
所以确实要压短提示词时，页面上有一个显式的「确认放行」（只压得住警告级，压不住拒绝级）。

警告的文案里必须带**具体数字**（"只有上一版的 40%（900 → 360 字符）"）：
"篇幅可疑"这种说法没法据以行动，而"掉了多少"才是判断"这是删减还是残缺"的唯一依据。

### 热更新：什么时候生效、什么时候不生效

这一页顶部那条提示来自接口（不是前端写死的文案），内容是：

| | 会变 | 不会变 |
|---|---|---|
| Agent 运行 | **下一次**运行（每次运行开始时读一次系统提示词） | **已经在跑的那一次** |
| 对话 / 结构化输出 | **下一轮**请求（每轮重新注入） | 已经算出去的那次 token 预算 |

**"已经在跑的那次不变"是刻意的**：中途换提示词会让同一份对话里前后两轮遵循不同指令，
于是报告里"它为什么这么选"变得无法解释。所以热更新的粒度是「下一次运行」，不是「下一步」。

> ⚠️ 这一条在实现上有个很容易想当然的坑，实测核过：
> `ChatClientBuilder.defaultSystem(Resource)` 在**构建 Client 的那一刻**就调用了
> `Resource.getContentAsString()`（用 `javap` 读的字节码）。也就是说
> **换一个"每次读都返回新内容"的 Resource 并不能让它热更新** —— 内容在启动时就被取走了。
> 所以热更新的落点只能在**调用点**（`ChatServiceImpl` / `StructuredChatServiceImpl`
> 每轮显式 `.system(...)`）。做错的现象是"改了提示词没反应"，而排查方向会跑到模型上去。

<p>

顺带一件事：`ai.chat.system-prompt-location` / `ai.agent.loop.system-prompt-location`
这两个配置项**在阶段四之后已经不影响运行时**了，它们只剩一个含义 ——
「出厂默认值与回滚去处的位置」（库空时拿它建第 1 版）。
**刻意保留而不是删掉**：一条看起来还在生效、实际已经不生效的配置，是最难查的一类问题。

### 假后端的版本状态机（为什么它必须有 `__reset`）

`web/mock/prompt-routes.mjs` 与其余几组假数据**性质不同**：它有四个**写**端点，
状态是**进程内可变**的 —— 因为界面自检要验的正是"点一下之后状态真的变了"。
代价与配套纪律：

- 状态只在内存里，**重启 `node mock/sse-server.mjs` 就回到初始**；
- 必须有 `POST /api/prompts/__reset`：否则自检跑第二遍时会继承第一遍改出来的版本号，
  「存一版之后版本数 +1」这类断言必红，而红的原因与功能无关
  （与 HITL 的 `__reset-approval` 同一条经验）；
- **校验逻辑照抄真后端的判据**。这一条最容易偷懒，代价很具体：
  假后端不校验的话，「提交坏提示词 → 界面逐条列出判据」这个分支**在自检里永远走不到**，
  等于没验证。这与"假数据里必须留一个没价格的模型"是同一条纪律。

假数据的初始状态刻意不是"万事如意"那一份：有两条历史版本、有一条带 `forkedFrom`、
**有一版没有署名**（界面必须显示「（未署名）」而不是空白 ——
"没署名"与"署名成了空"是两件事）。

## 第八种模式：告警与灰度（**这一页补的是"有人被通知"那半句话**）

阶段四的验收写的是「Agent 出问题**有人能查**、成本异常**有人能发现**、
Prompt 改坏**能回滚**」。在成本看板（第六种模式）之后，第二句只做到了一半：
看板能**看见**异常（`notes` 里那几条 ⚠️），而"看见"的前提是**有人恰好打开那一页**。
它的失败方式是最安静的一种：**没有人被通知**。

所以这一页有两块，各自补一句话：

| 块 | 补哪句话 | 端点 |
|---|---|---|
| 告警 | 把"人读的 ⚠️"变成**可查询、可确认、会自己出现和消失的事件** | `GET /api/alerts`、`/rules`、`/sweep`、`POST /{fp}/ack` |
| 灰度 | 把"新版到底比旧版好还是差"从"不可回答"变成"**有数据可答**" | `GET /api/canary`、`POST /canary/start`、`/stop` |

### 这一页最重要的一条纪律：配置与实测**同屏**

灰度那一块里，「我配了 20%」与「**实际分到几份**」是两个完全不同的东西。
分开显示的后果很具体：**配置 20%、实际 0 份时，只看配置的页面一切正常** ——
而那次实验等于没做，使用者却会据此得出"新版没有区别"。

所以 `SplitCard` 把它们并排摆出来（配置的重量 / 参与分流的运行 / 实验组 / 对照组 / 实测占比），
并且——**样本不足时不许显示"偏了多少"**，只显示"还差几份"。
理由：10% 的重量在 5 份样本里"一份都没分到"的概率高达 59%，
把那个比例摆出来，读的人一定会得出"分流偏了"，而那是噪声。

### 第二条纪律：构建阶段那一段必须显示成「这一页不评估」

判据目录现在**全部 8 条都是运行阶段的判据**，构建阶段（`GATE`）下**一个成员都没有** ——
原来那三条离线评测门禁（例如"离线评测基线漂移"）的判定依赖后端测试与 `rag-baseline.json`，
它们已在 2026-09-18 随后端测试代码一起删除。
但规则表**仍然分两段**：构建阶段那一段留着，写着「构建阶段（在 CI 上评估，这一页不评估）」
与"当前没有判据（0 条）"。理由是**一张空表头会被读成"构建阶段没问题"**，
而真相是这一页从来没有、也不该有构建阶段的结论 —— 这两种读法的区别正是这一段的全部意义。
将来再加门禁时，判据里的 `executedBy`（"谁在执行"）就是新一行的落点，界面会把它显示出来。

### 第三条纪律：三态必须长得不一样

`OPEN`（未处理）/ `ACKNOWLEDGED`（已确认）/ `RESOLVED`（已恢复）——
合成一个布尔的后果很具体：值班的人确认完一轮之后，列表看起来与"完全没人管"一模一样，
于是下一个人会从头再查一遍，而**第三个人就开始忽略这个列表**。
分开之后，「还有几条没人看过」是一个能直接读出来的数字（页面顶部那排统计里的第一格）。

### 三处刻意的交互决定

1. **「跑一轮评估」要点按钮**（进面板不自动跑）：
   它会**写库**（新响的落库、恢复的标记），自动跑会让"打开这一页看看"这个动作本身
   改变告警状态。⚠️ 代价必须说清：**没有人点就永远没有告警记录** ——
   真上生产要挂定时器（`GET /api/alerts/sweep` 是普通 GET，cron 直接打）。
2. **写操作的失败分两类，界面说两句不同的话**：
   400（参数不合规，改输入再点）与 409（前提过期，**刷新后重试才有意义**）。
   两者都渲染成一句红字的后果是：使用者会对着 409 反复点同一个按钮。
3. **空态必须解释自己**：清单为空时说"要么一切正常，要么还没跑过评估"；
   没有候选版本可选时说清"为什么"并指向下一步（去 Prompt 面板存一版）。
   只渲染一个空表格的后果是使用者以为界面坏了（而他什么也没做错）。

### 假后端（`mock/alert-routes.mjs`）

7 个端点，其中 4 个是**有状态**的（确认告警 / 开灰度 / 停灰度 / `__reset`）。
初始数据**刻意不是"万事如意"那一份**：

- 三种状态**各一条**（未处理 / 已确认 / 已恢复）—— 否则"三态必须长得不一样"那条断言
  永远走不到；
- 构建阶段**一条都不给**（0 条）—— 与真后端的判据目录一致（那三条离线评测门禁随后端测试一起删了；
  假数据多一条判据不会有任何症状，而这正是"假数据与真代码漂移"最常见的形态）；
  界面上"这一段必须写明**当前没有判据（0 条）**、而且不许只留一张空表头"那条断言，正是靠这个 0 条走到的；
- 灰度**默认是进行中的**（配置 20%、实测 3/14）—— 否则"配置与实测同屏"没东西可看。

⚠️ 与 `prompt-routes.mjs` 同一条经验：既然是状态机，就必须有 `POST /api/alerts/__reset`，
否则自检脚本跑第二遍时会继承第一遍改出来的状态（第十二轮实测踩过）。

⚠️ 还有一条**这一轮新踩出来的**：假数据里的默认值必须与真后端**同一个名字**
（`kind` 用 `system-agent-tools`，不是枚举名 `agent-loop`）——
第一版两边各写了一遍，于是真后端 400 而假后端全绿（这正是「默认参数里的字符串两边各写一份，真后端 400 而假后端全绿」那个形状）。
现在有一条跨路径断言盯着这个名字。

## 第九区：用户管理（账号 / 口令 / 启用状态）

这一区管的是"**谁可以用**"。账号落在 `agent_user` 表里（登录名 + PBKDF2 口令散列 + 启用状态），
端点全在 `/api/permissions/**`，后端那一侧的判据与实测见
[docs/项目功能点与代码索引.md 的 5.8](../docs/%E9%A1%B9%E7%9B%AE%E5%8A%9F%E8%83%BD%E7%82%B9%E4%B8%8E%E4%BB%A3%E7%A0%81%E7%B4%A2%E5%BC%95.md)。
这一节只写**界面这一侧**的取舍。

### 顶部那块边界说明已经删除

原来两页顶部有一块 warning（「这一层现在没有登录：/api/permissions/** 是匿名的」+ 口令散列 +
初始管理员），已按需求整块删掉。它说过的两条事实仍然成立，只是不再由页面顶部来说：

- **这一族端点没有登录**（能访问端口的人可以给自己开「全部工具」）：这条事实写在
  `docs/项目功能点与代码索引.md` 的 5.8 与 `application.properties` 的注释里，
  关掉它的开关是 `ai.agent.permission.management-enabled`；
- **口令只以散列保存、响应里没有这一列**：「改口令」弹窗与「新建账号」弹窗各自写着这一条
  （找不回来，只能重设）。

### ★ "新建的账号一个角色都没有 → 没有任何权限"要说出来

账号行上的橙色标签（`没有角色 → 没有任何权限`）与建号成功的反馈那句话各写一遍 ——
**这不是重复**：它们在不同的操作路径上（看列表时 / 刚建完时），
而漏掉任何一处，那一处的使用者就会得到相反的结论（以为"新用户默认能用"）。

### 为什么这一页没有"删除账号"，只有一枚开关

后端刻意不提供删除（`AccountMapper` 里没有那个方法，理由见它的类注释）：
删掉一行会让它名下的授权关系被外键级联带走，于是"这个人当时是什么权限"这个复盘问题永远没有答案。
**停用是它的等价物** —— 停用的账号在解析期一律没有权限，而重新启用会把它原来的角色带回来。
所以行上那枚开关与「编辑」弹窗只做启用/停用与显示名，没有删除按钮。

### 角色那一列是只读的

账号表显示"他属于哪些角色"，但**不给编辑入口**：账号↔角色关系的编辑只在「权限管理」那一页
（角色记录的「成员」）—— 同一份关系有两个界面入口就是两份判据，而它们不一致时页面上看不出来。
列标题里写着"编辑在「权限管理」里"，自检里有一条断言盯着"这一页没有「角色」按钮"。

### 自检为这一区钉了什么

`[8.6]` 一节（假后端路径），其中值得单独记的是：

- **账号表上没有「角色」按钮**（角色归属只在角色侧编辑）；
- **同名账号 409 被界面说成「名字已被占用」**（而不是一句"操作失败"）；
- **编辑弹窗改显示名 + 停用** → 反馈用的是后端那句话，行上出现停用标记；开关点回去 = 重新启用
  （"没有真删除"这件事在界面上是可验的）；
- **改口令成功，反馈说明旧口令立即失效**；
- **真后端那条路径上这一节一个字节都不写库**（凡是"造数据"的断言都只在假后端跑）——
  与 Prompt 面板那条"真路径不往库里塞版本"同一条纪律。

## 第十区：权限管理（角色 / 工具白名单 / 目录前缀 / 角色成员）

这一区管的是"**能用哪几把工具、能在哪些目录下干活、谁有这个角色**"。
它由四张表支撑（`agent_role` / `agent_role_tool` / `agent_role_dir` / `agent_user_role`），
与用户管理共用同一份快照（`GET /api/permissions` 一次取回账号 + 角色 + 可分配工具）。

### 角色行上四个编辑入口，各开一个弹窗

「编辑」「工具」「目录」「成员」是四件独立的事，各对应一个写端点，而每个端点提交的都是**一整份清单**
（后端整体替换，不是逐条增删）。合成一个"保存"去提交全部，会让"只改目录"也去重写工具清单与成员 ——
界面上每一处改动的影响面必须与后端那条"整体替换"的语义对齐。

### 角色表里没有「成员」列

"谁有这个角色"不在表里 —— 点「成员」时才查：弹窗里勾着的就是它的全部成员（看与改在同一处，
不会有两份说法）。角色表因此只留"这个角色配了什么"（工具 / 目录）两栏。

### 成员弹窗：账号↔角色的编辑只在这一侧

弹窗里勾的就是这个角色**全部**的成员。两个取值上的取舍：

- **停用的账号也在候选里**：停用即无权限那条判据只在解析期生效，"停用期间配好的角色，
  重新启用之后就生效"比"配的时候就拒"更符合直觉；
- **一个都不勾 = 成员清空**，这时给一条警告条：「一个账号都不勾 = 这个角色没有成员 ——
  它的工具白名单与目录前缀对谁都还不生效」。这句话与用户管理页的
  "新账号没有角色"**不是同一句**：主语不同（角色 / 账号），后果也不同。

### 权限 = 角色的并集，所以这一页没有"权限矩阵"

角色表的两栏（工具 / 目录）是**配置**，而"某个人实际能干什么"只在核对卡里算。这是后端的设计
（多对多取并集）在界面上的直接后果，而且它挡住了一类误读：一张"账号 × 工具"的彩色格子表
会让人以为权限是**逐条配在账号上**的，于是"给这个人多加一把工具"会被当成一次普通编辑 ——
而它其实是一次**授权**，事后必须能回答"是谁、通过哪个角色给的"。

### 角色表里那两栏为什么用标签而不是下拉

「能调的工具」与「能在哪些目录下干活」都是**读**的位置（改它们要点「工具」/「目录」进弹窗）。
两栏在**清单为空**时给的是橙色标签而不是空白 —— 空白会被读成"这一栏没数据"，
而真相是"这个角色的成员一把工具都调不到"。

### 核对卡：这一页唯一"能自己回答一个问题"的地方

四个控件（账号 / 工具 / 目录 / 核对）与一段结论。它存在的理由是：
"这个人到底能不能干这件事"**不该靠人把三张表在脑子里拼一遍**。
结论块里同时给出工具那一半、目录那一半、命中的前缀、他拥有的角色、以及他实际能调的工具清单 ——
一屏之内把"为什么是这个结论"讲完。

⚠️ 它的结论与运行期读的是**同一份解析**（`UserPermissions`），
但**运行期现在还没有消费这一层**（见 5.8 的缺口）—— 所以页面上不能写"这次运行会按它执行"。

### 假后端那一份是照搬判据的

`web/mock/permission-routes.mjs` 与别的假后端有一处**本质区别**：它把真后端的判据也抄了一遍 ——
工具名对注册表（写错一个字母要回 400 且带可用清单）、同名 409、目录按**路径分段**比
（`D:\work\demo` 不命中 `D:\work\demo-other`）。不抄的话，"界面能不能把后端的拒绝显示清楚"
这个分支在自检里永远走不到 —— 而那正是这一页最需要被验的部分。

它同时是一个**有状态的假后端**（10 个写端点），所以必须配 `POST /api/permissions/__reset`：
自检跑两遍，第二遍不能继承第一遍造出来的账号与角色。⚠️ 成员那个新端点（`PUT /roles/{id}/users`）
也照搬了真后端的判据：**未知 userId → 400 且报错里带可用账号清单**，且回执里的成员**包含停用账号**。

### `GET /users/search` 是 agent任务那一页的选人下拉，不是这一页的界面

这一页自己不画搜索框（它一次取回全量快照就能画完两张表），但这一族里多了一个
`GET /api/permissions/users/search?keyword=&limit=`：agent任务那一页用它把"发布人 / 任务人"
做成搜索选择器（见第十一区）。它的返回体刻意是**瘦的**（id / name / displayName / status /
statusLabel / usable，**没有 roles**）：那个字段下拉里不显示，而照搬快照的装配会让响应里写着
`roles: []` —— 那是"这个人没有任何角色"，与"这次没查"是两件事，在 JSON 里却长得一样。

假后端那一份也照着来：空搜索词 **400**、`limit` 默认 5 上限 20（超限夹住并回显实际值），
并且它把账号表的查询**导出**给 task-routes 用 —— "发布人 / 任务人是不是真实用户"这条判据
只读一份账号表，两边各写一份的话，"假后端说这个人是真的、真端点说不存在"只会表现为自检里一句 400。

### 自检为这一区钉了什么

`[8.7]` 一节（假后端路径），其中值得单独记的是：

- **角色行上有五个入口**：编辑 / 工具 / 目录 / 成员 / 删除（顺序也钉着）；
- **角色表里没有「成员」列**：谁有它要点「成员」进弹窗才查（表头断言钉着）；
- **核对卡对同一份数据给出两种结论**：没有角色的账号被判「不允许」并列出"能调的是 []"；
  管理员在 `D:\work\demo-other` 上被判「不允许」（证明目录是按段比而不是按字符串前缀比）；
- **写错一个字母的工具名 → 400 且报错里带可用清单**（这条直接打接口：界面上的复选框给不出错名字）；
- **成员弹窗写入的就是 `PUT /roles/{id}/users`**，且清空时会明说"一个成员都没有"；
- **未知 userId → 400**，以及**账号侧的 `PUT /users/{id}/roles` 仍然可用**（两侧同一张关系表）；
- **真后端那条路径上这一节一个字节都不写库**（凡是"造数据"的断言都只在假后端跑）——
  与 Prompt 面板那条"真路径不往库里塞版本"同一条纪律。

> ⚠️ 自检里两字按钮的正则要容忍一个空格：antd 6 的 `Button` 会把**两个汉字**拆成「编 辑」
> （`split('').join(' ')`，源码在 `buttonHelpers.js` 的 `splitCNCharsBySpace`）——
> 写成 `/^编辑$/` 时连真的按钮也匹配不上，而**"按钮不存在"这类断言会因此假绿**。

## 第十一区：agent任务（派活 / 确认 / 执行 / 验收）

这一区管的是"**这件活现在等谁**"。一次派给 Agent 的活从发布到验收要经过几个人的确认，
落在 `agent_task` / `agent_task_confirm` 两张表里，端点全在 `/api/agent-tasks/**`，
后端那一侧的状态链与实测见
[docs/项目功能点与代码索引.md 的 5.9](../docs/%E9%A1%B9%E7%9B%AE%E5%8A%9F%E8%83%BD%E7%82%B9%E4%B8%8E%E4%BB%A3%E7%A0%81%E7%B4%A2%E5%BC%95.md)。
这一节只写**界面这一侧**的取舍。

### 为什么是卡片看板，而不是这一区另外两页那样的表格

用户管理 / 权限管理回答的是"配置成什么样"（一张表能看全），而这一页回答的是
"**现在有哪几件事、各自卡在哪**"。同一个答案画成表格只有"状态"一列能看出差别，
画成按状态分列的卡片则一眼看出"有三件事在等人确认"——
而且点开一张卡片就是它自己的那条链（确认项从上到下就是流转顺序）。

### ★ 卡片停在哪一列 = 现在等谁

列的归属**由后端算**（`AgentTaskService.Column`：新任务 / 待处理 / 执行中 / 待验收 / 已完成（含已取消）），
前端只按 key 画。前端自己再算一遍"哪个状态进哪一列"就是第二份判据，
而两份不一致时卡片会出现在错误的列上 —— 那时"现在等谁"这个问题的答案就是错的，且没有任何报错。

列头上写着这一列收的是哪几种状态（「待处理」= 待确认需求 / 待确认计划 / 待授权），
卡片上写着当前执行人。没有这两样，"待处理"只是一个堆着东西的筐。

### 卡片上的长文字默认夹住，夹掉了才给「展开全文」

任务描述可以很长，执行结果更是一份多行产出（假数据里那种「产出 / 改动 / 运行」三段）。
**标题与执行结果各最多露 6 行**（`Clamped.tsx` 的 `max-height`，行高统一 18px），
更多的字被挡在外面；真的挡住了的卡片，行末出现一个「展开全文」，点开露全部、再点收起。
判据是这一页唯一的答案要留得住 —— "现在有哪几件事、各自卡在哪"：一张写着长产出的卡片
把整列撑高之后，同一个窗口里就只剩两三张卡可见。

三处刻意的取舍：

| 取舍 | 为什么 |
|---|---|
| **展开入口画在卡片上**，不是"想看就去点详情" | 一列里摆着好几张卡时，哪一张被夹掉靠比对各卡高度是看不出来的；而点详情要离开看板 |
| **开关只在真的夹掉了才出现** | 描述只有一行时画一个点了没反应的「展开」，比不画更糟 —— 判据是内容高度高过上限（见下） |
| **卡片整张可点改成"叠一层透明 button"** | `button` 里不能嵌 `button`，而「展开全文」必须是真按钮（键盘用户要能按到）。代价是卡片上的字选不中 —— 要选中一段话去详情弹窗（那里的文字是可选的） |

**"有没有被夹掉"必须在浏览器里量**，不能按字数猜：同一个描述在窄列里会换行、
在宽列里不会，而列宽是 `flex` 算出来的。所以 `Clamped` 拿
`scrollHeight`（完整内容的高度）比调用方给的那个上限，并用 `ResizeObserver`
盯住这一段自己的尺寸 —— 换一条任务、窗口缩放都会重算。

> ⚠️ **判据与渲染是两条路，这是这一版唯一"必须这么写"的地方**。
> 展开**不能**靠"把 `max-height` 去掉"来表达：`useEffect` 在样式重算之前跑，
> 挂载时若按展开渲染再拿量出来的结果去收，`clientHeight` 会是展开时的高度 ——
> 结论永远是"没夹掉"，开关不出现，卡片停在展开态回不去（实测：内容 162px / 露出 162px）。
> 现在上限那个常数留在行内（判据读它），"展开"由 CSS 的 `.is-open` 用 `!important` 压过去。

> ⚠️ 自检这一条**量的是几何，不是文字**：`overflow: hidden` 之下被挡住的字**一直在 DOM 里**，
> 所以 `toContainText('…')` 之类完全断不到它（第一版就是这么写的，直接假绿）。
> 现在断的是"收起时内容比露出来的地方高""展开后两者相等""再点收起回到原来的高度"，
> 并且在读几何**之前先等它量完**（首帧一律按没夹掉渲染，直接读会读到那一帧）。

### ★ 「执行中」那一列收**四个**状态

已确认需求 / 已确认计划 / 已授权 / 执行中 —— 它们对看板是同一件事：**球在 agent 手上，人点不动**。
分成四列的话，一眼看去像是"有四件事在等我"，而其实一件都不在等；
四个状态的进度差别靠卡片上的状态标签表达（列头会把四个都写出来）。
它和「已完成」收两个状态（已完成 + 已取消）是同一条取舍的两处应用：
**列的归并按"对用户是什么"来分，不按状态个数来分。**

### 等 agent 的那几格不画推进按钮，但要说明为什么

新发布、已确认需求、已确认计划、已授权这四格只有「取消任务」，详情里另给一句
"这一步由 agent 任务执行做"（它按状态往下走：判需求有没有歧义、拆任务点、问授权、开跑；
跑完自己转到「待验收」）。画一个"看起来能推进"的按钮比不画更坏 —— 用户会反复点，
每次都回一句"当前状态不允许"。

那句提示的判据是**「有动作、但既不能答复也不能推进」**，而不是一份状态名清单：
状态有哪些、哪几个由 agent 处理是后端的定义，前端再抄一份就会在后端新增一格时漏掉它。

### 按钮来自后端的 `actions`，前端不 `if` 状态

详情接口每次返回 `actions`（`advance` / `answer` / `cancel` 各自带一句按钮文案），
界面照着画。前端自己判断"这个状态该显示什么按钮"的话，它会与后端的状态机漂移，
而漂移的现象是"按钮点得下去、点完回 409"——用户会以为是自己操作错了。
同一句话反过来：**409 与 400 在界面上必须长得不一样** ——
前者说"这条任务的状态已经变了"（并顺手刷新看板与详情，让人直接看到它到哪一步了），
后者才是"你填的东西不合规"。

### 「已取消」不单列一列，卡片并进「已完成」

看板只画"这件事结束了没有"，而验收通过与取消都是结束：给已取消单开一列，
会让一条流程里最边缘的结局占掉一整列宽度（而且大多数时候是空的）。
两者同列之后，区别靠卡片上的**状态标签与取消原因**表达 —— 所以取消原因必须画出来，
否则那一列里"验收通过的"与"被取消的"看起来会是同一件事。
列头写着这一列收的是哪两种状态（后端给的 `statusLabels`），点开卡片还能看到取消原因与整条确认链。
归并写在**后端的列定义**里（`AgentTaskService.Column`），前端只按返回的列画 ——
前端再算一遍就是第二份判据。

### 「新发布」与「待确认需求」是两件事，界面上要说出来

新发布的任务**还没有确认项**（它等 agent 判需求：有歧义就生成一条需求确认项、
没有就直接进「已确认需求」），待确认需求的任务有一条在等他答。
两个状态挨着，说反了会让用户去找一个不存在的按钮 —— 所以详情里那一行写的是
"还没有确认项 —— 「新发布」的任务等 agent 判断需求有没有歧义"。

### 发布弹窗：发布人 / 任务人是**搜索选择器**，agentId 没有输入框

发布人与任务人都必填，而且都必须是账号表里真实存在的用户（后端 `DefaultAgentTaskService#realUser`
拿 `agent_user` 核一遍，不存在 → 400）。界面上那两格因此不是一个能打字的输入框，
而是一个搜索选择器（`UserPicker`）：

- **搜索词进后端**（`GET /api/permissions/users/search`，antd 那一侧 `filterOption={false}`）：
  候选是整张账号表，"一次全取回来"在账号多时就是"为了填一个名字下载一张表"；
  而 antd 自带的前端过滤只过滤已经取回来的那几条 —— 那会让"搜不到"看起来像"系统里没有这个人"；
- **没输入就不发请求**：空搜索词在后端是 400，它刻意不退化成"把前几个账号给你"；
- 候选那一行是「显示名（登录名）」，**停用的账号也出现**并带一个标记 ——
  它仍然可以选："当时派给谁"与"他现在能不能登录"是两件事；
- 选中的那一条会一直留在候选里：候选列表每次搜索都被替换，不留住的话选完再搜下一个词，
  之前那一格会退化成裸的登录名（看起来像没选中）。

**agentId 不在这个表单里**：它由平台在第一次接手这条任务时写入，值来自配置
`ai.agent.task.agent-id`（本应用在 Agent 应用注册表里的 id）。让发布人打一个数字，
等于把"这个 id 对不对"变成一个人的记忆，而填错不报错 —— 卡片上会写着 `agent#7`，
而那条运行其实不属于任何一个 Agent 应用。

### 详情里的确认项：答过的与待答的必须一眼分得开

等答复的那一条有橙色左边框与浅色底（它是这一页唯一"现在该动"的东西），
答过的是绿色。每条上写着第几步、哪一类、问的是什么、给了哪些选项、用户答的是什么 ——
选项集画成可按的按钮，选项之外想补充的话写在同一个框里（两者走同一个端点，
因为后端存的是"用户确认项"这一个字段）。

### 假后端照搬的是**状态链**，agent 那几格**显式推**

`web/mock/task-routes.mjs` 与 permission 那一份同一类（有状态 + `__reset`），
但它要照搬的是**推进到哪一步、落到哪一格、当前状态不允许的动作回 409**。
不照搬的话，"点一下卡片真的换列了吗"这件事在自检里永远走不到 ——
而那正是这一页的全部内容。初始数据刻意覆盖**全部五列**：其中「执行中」那一列放**四张**
（四个状态归并成一列是这一版的判据，只放一张就看不出这件事），「已完成」那一列放**两条**
（一条验收通过的、一条已取消的）—— 那一列收两个状态，只放一条也看不出这件事。

真后端那四格由一个**定时任务**驱动（判定调模型、执行跑 Agent 运行），假后端不调模型，
而是给两条**可判定的规则**（描述里带「需要补充」→ 判成有歧义；带「小任务」→ 只拆 2 个任务点），
并且**不自动推**：`POST /api/agent-tasks/__run-agent?id=&steps=` 显式推一轮。
跟着写端点自动推的话，"发布之后卡片落在哪一列"会取决于推的时机，自检就没法断言了；
而 `steps=1` 让自检能盯住**每一格**（新任务 → 执行中 → 待处理）。

### 自检为这一区钉了什么

`[8.8]` 一节（假后端路径），其中值得单独记的是：

- **五列都在、每一列都有卡片**（分组验得出来）；
  **「执行中」那一列的列头写着四个状态、列里四张卡片各带自己的标签**；
  **「已完成」那一列里同时有验收通过与取消的两条**，已取消那条带着取消原因；
- **「新发布」没有推进按钮**，并且详情里写出了"这一步由 agent 任务执行做"；
- **推一格：卡片从「新任务」移进「执行中」（已确认需求）**；再推一格到「待处理」（任务点 ≥ 5 要确认计划），
  计划确认项的正文里带着拆出来的 5 个任务点；
- **答复之后不再生成下一条确认项**（下一条由 agent 那一步生成：答复计划 → 已确认计划，
  确认项一条不少地都是已答状态）—— 这是这一版与上一版最不一样的一条；
- **409 那条路**：脚本先替"另一个人"答掉当前确认项，界面上那个按钮**看起来还能点** ——
  点下去必须出现"这条任务的状态已经变了"；
- **发布表单里没有 agentId 这一格**（说明文字里写着它由平台在接手时写）；
- **两格选择器都真的走了一遍搜索**：搜 `adm` 选到「初始管理员（admin）」、搜 `li` 选到停用的「李工（li）」
  —— 后者顺带验了"停用账号也在候选里、且带标记"；
- **发布出来的任务 agentId 是空的**（卡片上还没有 `agent#…`），平台接手（`__run-agent`）之后
  卡片上才出现 `agent#1`；
- **发布与取消各走一遍真实表单**，卡片进对列、原因显示在卡片上；
- **长描述那张卡片给出「展开全文」，并且它真的管用**：收起时内容比露出来的地方高、
  展开后两者相等、再点收起回到原来的高度（量几何，不断文字 —— 理由见「卡片上的长文字」那一节）；
- **真后端那条路径上这一节一个字节都不写库**（与前面两区同一条纪律）。
